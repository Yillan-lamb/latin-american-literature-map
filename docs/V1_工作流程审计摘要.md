门禁历史中，共有 15 个任务接受了首次独立复核：4 个在 R0 通过，11 个在 R0 被要求差量返修；其中 10 个在 R1 通过，1 个继续到 R2 后通过。这个分布说明返修不是偶发异常，而是 V1 质量控制的主要组成部分；同时也说明共享结构验证不能替代独立语义审核。

## 2. V1 实际跑通的工作流

V1 实际链路不是单次“资料→数据库”，而是五段带门禁的流水线：

```text
治理与范围基线
→ 用户 N1
→ 私有资料接收、来源临时编号、正式 SRC 分配、L0/L1 OCR、覆盖盘点
→ 两位作家试点：来源筛选、L2 内容单元、候选实体/事实/关系、PRE 包
→ Codex 正式暂存、SQLite/CSV/JSON 试点、用户 N2 冻结 Schema 0.2
→ 三个串行研究批次 B01—B03：来源→候选→Worker 自检→Codex Reviewer→差量返修
→ 阶段 4：权威补证、跨批次消歧、来源去重、关系/事实准入、内容卡和覆盖审计
→ legacy 审计与 research_gap 止损
→ 外部 AI 只做 A06 PRE 机械预组装
→ Codex 分配正式 ID、构建 V1 CSV/JSON/SQLite/Excel、运行 QA
→ 用户 N3 决定门槛与 Schema 0.3 加法升级
→ 重新构建、最终一致性/引用/公开边界审计
→ 用户 N4
→ PR、main、v1.0.0 标签和 GitHub Release
```

其中真正有效的控制点是：来源身份门禁、候选/hold/正式数据分层、独立语义复核、Codex 单线程整合、四格式一致性验证、用户只审核方向性节点。

## 3. 有效做法

1. **来源 ID 与题名双锚点。** `SRC-XXXX`、来源题名和稳定 URL/标识符使事实与关系能够回查。
2. **候选与正式数据分离。** Worker 只产候选，正式 ID、实体合并、Schema 和 SQLite 写入留给 Codex。
3. **事实型与解释型关系分层。** 直接事实可由一项合格来源支持；解释关系原则上双独立来源，单来源进入 hold。
4. **显式不确定状态。** `hold_needs_second_source`、`disputed`、`unclear`、`research_gap`、`rejected` 防止为了数量制造确定性。
5. **Worker / Reviewer 分离。** 27 轮独立门禁发现了共享机械验证未发现的来源层级、对象层级和语义问题。
6. **差量返修。** R1/R2 只修失败记录，要求“保持不变、禁止新增、重新验证”，避免全包重做。
7. **单线程正式整合。** 外部 AI 不写 `data/`，共享实体、正式 ID 与关系池由 CODEX-DATA 统一处理。
8. **自动机械 QA。** CSV 标准解析、ID、引用、SQLite 完整性、外键、跨格式哈希与 MANIFEST 显著降低结构性错误。
9. **节点式 Git。** 早期逐文件小提交被 S3/N3/N4 里程碑提交取代，公开边界和版本冻结更清晰。
10. **用户只参与 N1—N4。** 普通缺口、访问受阻、译名冲突和窄范围纠错没有反复打断用户。

## 4. 主要问题

### 4.1 建设期任务包装过重

FULL 包通常包含 README、STATUS、QA、ISSUES、HANDOFF、MANIFEST 和多张主体表。它适合 OCR、批量研究和迁移，但不适合补一个年份、一个 URL 或一条来源。以后日常增量默认使用 LITE 或内部最小变更记录，只有高风险研究、OCR、批量迁移才使用 FULL。

### 4.2 多文件重复数字导致漂移

STATUS、QA、HANDOFF、README、SUMMARY、ISSUES、MANIFEST 多次抄写同一计数。A06-A 主体 CSV 正确，仍因三份过程文档写错 49/50、3/4、A/C 与 A/A 而返修。以后数字必须由脚本生成；过程文档引用机器报告，不手工复制完整分布。

### 4.3 机械 pass 不等于语义 pass

共享验证能发现错列、重复 ID 和禁止文件，却不能判断索引页是否为论文、会议摘要是否为 A 级、同名短篇是否支持整部作品集，也不能判断作者级观点是否被下推到作品。Reviewer 必须保留代表性语义抽核。

### 4.4 状态在展示层被旁路

A04 的关系表保持 hold，但内容卡把相同解释写成确定属性；hold/research_note_only 也被放进“已准入事实素材”。以后内容卡、网站数据和摘要只能消费已准入视图；hold/gap 必须进入独立说明区并保留来源归属措辞。

### 4.5 当前“SQLite 唯一主数据”尚未工程化

章程规定 SQLite 是唯一主数据，但 `scripts/build_v1_candidate.py` 实际从 PRE、来源映射和 CSV 组装内存表，再同时写 CSV、JSON、SQLite；Excel从 CSV 生成。V1 四格式逻辑一致，但 SQLite 不是实际编辑源。下一次正式增量前应把 V1.0.0 SQLite 提升为 `data/master/` 主库，并建立“迁移脚本→SQLite→导出”的通用工具链。现有 V1 构建脚本应保留为历史快照重建器，不再直接用于增量写入。

### 4.6 验证脚本是版本快照，不是增量验证器

`scripts/validate_v1_candidate.py` 固定断言 74/144/76/238 等 V1 数字及具体 ID，适合验证 v1.0.0，不适合新增数据。必须拆为：动态不变量验证器、导出一致性验证器、可选的发布快照回归验证器。

### 4.7 正式发布物仍使用 candidate/staging 命名

`data/staging/v1_candidate/README.md` 仍写“不是 N4 正式发布版”“N4 前”，但该目录已随 v1.0.0 正式发布。这不会改变数据内容，却会误导接手者。建议以后建立 `data/master/` 与 `data/exports/<version>/`；历史目录保留只读并明确为 V1.0.0 发布快照。

## 5. V1 真实踩坑与防错规则

| 实际问题 | V1 例子 | 以后强制规则 |
|---|---|---|
| CSV 错列 | 英文逗号未转义导致 13 列对 12 列 | 只用标准 CSV 库写出；写后重新标准解析并断言列数 |
| 非法枚举 | `open_access（部分）` | 枚举由 Schema/任务卡读取；断言实际值是允许集合的子集 |
| 人工数字漂移 | 49/50、235/237、A/C 与 A/A | 所有计数从最终数据机械生成；文档不手抄多份统计 |
| 索引页冒充论文 | Borges Studies Online 索引被标 A | 来源对象必须具体到作者、题名、载体、年份和稳定标识；索引只作发现线索 |
| 聚合页冒充原始页 | CAPES 代替原期刊页面 | 原机构/原期刊落地页为主；聚合页只能交叉或 discovery |
| 作者页冒充单书页 | Rocco 作者聚合页代替产品页 | 页面对象必须与事实对象同层级 |
| 未访问却称已核验 | 403/验证码页面仍被写可访问 | 实际打开；记录访问日期、页面标题、状态；被拦截则如实 hold |
| 标题级关联当直接证据 | 论文标题并置作品/事件 | 标题只能作间接线索；直接关系需要正文或明确书目表达 |
| 同一来源重复计数 | 同一论文标题与正文算两源 | 按独立作品/研究成果计数，不按 URL 或页面数量计数 |
| 对象层级错配 | 同名短篇研究关闭作品集 research_gap | 证据对象必须与目标实体层级一致；局部支持只能 partial |
| 来源等级过高 | 会议摘要被当 A 级论文 | 以实际可核验出版形态定级，不因平台学术化自动升 A |
| 复合事实不原子 | 1958 写作年/1980 出版年塞入首发年 | 一个事实字段只表达一个语义；不同事件拆行 |
| 常识挂错来源 | 来源未显示生卒年仍保留事实 | 低置信度不能弥补无证据；补合格来源或删除/转 gap |
| 题名推断关系 | 英文选集被推为完整译本 | 不从题名、关键词共现或常识生成正式关系 |
| 文学人物与历史人物合并 | el Consejero 与 Antônio Conselheiro | 类型不同默认分离；“原型/对应”没有 Schema 时只作 research note |
| 作者级观点下推作品 | 作者政治身份被写成具体诗集主题 | 证据必须直接指向目标作品；作者级材料保持 author-level |
| hold 在卡片中确定化 | 单来源关系写成作品固有属性 | 卡片从准入视图生成；单来源解释必须来源归属式表达 |
| 重复 ID / 断裂端点 | 缩写 ID、`等`、broken relation | ID 字段只允许完整可解析 ID；入库前主键与外键全量断言 |
| Worker 越权 | 自分配正式 ID、宣布 pass、解锁阶段 | Worker 只写候选和自检；最终 verdict、正式 ID、SQLite 和节点由授权角色处理 |
| 导出物作为独立事实源 | CSV/JSON/Excel分别维护风险 | 只写 SQLite；其他格式全部重建，禁止手工回写为事实 |

## 6. 简化后的长期流程

```text
新增请求
→ 分类（来源/实体/事实/关系/hold/纠错/批量）
→ 查重与版权边界
→ 来源登记或复用 SRC
→ 最小候选变更集
→ 机械自检
→ 独立 Reviewer（事实证据与语义）
→ Data Integrator 分配正式 ID并以迁移写入 SQLite
→ 动态 QA
→ 从 SQLite 重建 CSV/JSON/Excel
→ 导出一致性与公开边界检查
→ CHANGELOG + SemVer 判定
→ 发布候选；需正式发布时由 USER 处理版本节点
```

单条事实只跑与其相关的查重、证据、审核、迁移和 QA；不重复 OCR、覆盖审计、全量策展或 N1—N3。批量新增才启用分 batch、FULL 包和覆盖审计。

## 7. 实施优先级与剩余事项

本次审计修订已完成前四项；剩余事项在第一次实际增量或涉及新字段时执行：

1. ✅ 从 v1.0.0 SQLite 建立正式 `data/master/` 基线；
2. ✅ 新建通用迁移入口和迁移日志；
3. ✅ 新建 SQLite→CSV/JSON/Excel 导出脚本；
4. ✅ 把当前硬编码验证器拆成动态不变量验证与 v1.0.0 快照回归验证；
5. ⬜ 在新增网络来源或字段时补充 URL 核验状态/日期和 JSON Schema；
6. ✅ 修正文档冲突清单中标为“当前误导”的文件。

这些修订不改变 `PROJECT_CHARTER.md`。剩余工程增强涉及正式 Schema 或公开契约时，仍须形成独立任务卡、迁移记录和 Reviewer 门禁。
