# 拉丁美洲文学地图：数据新增与版本维护操作手册

- 版本：1.1（审计修订版）
- 生效日期：2026-08-11
- 适用范围：V1.0.0 发布后的数据新增、补证、纠错、批量扩展、导出和版本维护
- 维护角色：CODEX-PM / CODEX-REVIEW / CODEX-DATA
- 最高约束：`project/governance/PROJECT_CHARTER.md` 1.4.0

本修订版已落实 V1.0.0 审计提出的文档入口统一、V1.0.0 快照标识、SQLite 主库基线、动态主库验证和通用导出工具。工程入口分别为 `data/master/V1_MASTER.sqlite`、`scripts/apply_migration.py`、`scripts/validate_master.py` 和 `scripts/export_from_sqlite.py`。

## 1. 手册用途

本手册把 V1.0.0 建设过程中已经跑通的研究、审核、数据整合和发布方法，转换为长期增量维护 SOP。未来用户只需说明新增对象和资料，维护 AI 应自行完成任务分类、查重、来源处理、候选生成、审核、正式整合、QA 和版本建议，不要求用户复述 V1 历史。

本手册不是新章程，也不修改 `project/governance/PROJECT_CHARTER.md`。如本手册与更高层文件冲突，立即服从更高层文件并记录冲突。

核心原则：

1. 最小增量：只执行与本次变化有关的步骤。
2. 来源先于数据：没有来源 ID 和来源题名，不进入正式数据。
3. 候选先于正式：研究结果先进入候选，不直接写主库。
4. 机械 QA 与语义 Reviewer 双门禁。
5. SQLite 是唯一正式主数据，其他格式全部重建。
6. 无法确认时 fail-closed：candidate / hold / disputed / research_gap，而不是猜测。
7. 用户只处理方向、政策、重大 Schema、不可逆操作和正式版本节点。

## 2. 权威规则

遇到冲突时依次采用：

1. 用户当前明确指示；
2. 当前有效 `project/governance/PROJECT_CHARTER.md`；
3. 当前项目决策记录；
4. 当前研究与数据规范；
5. `project/tasks/TASKS.md`；
6. 具体任务卡；
7. 历史报告、旧任务包、旧聊天和旧实现说明。

当前必须牢记：

- V1 最低关系门槛是 75，150 是 V1.1 扩展目标；
- 当前 Schema 是 0.4，共 14 个正式关系词；
- `BASED_ON_EVENT` 仅允许 `work → event`；
- `APPEARS_IN` 仅允许 `character → work`，不保存 inverse；
- author→event 没有正式关系词，只能作事实说明或兼容性候选；
- 旧文件中的 Schema 0.2、150 条 V1 门槛和“N4 前候选”只在历史语境有效；
- 未经用户明确授权，不得修改 `project/governance/PROJECT_CHARTER.md`。

## 3. V1 工作流程审计结论

V1 实际采用了“治理节点 + 外部候选生产 + Codex关键门禁 + 单线程整合 + 用户方向审核”的流程：

```text
资料进入
→ 来源登记与合法性边界
→ 必要 OCR / 内容单元整理
→ 候选实体、事实、关系和卡片素材
→ Worker 机械自检
→ 独立 Reviewer 来源与语义复核
→ 差量返修
→ 跨批次查重、规范化和 hold/gap 分层
→ Codex 分配正式 ID
→ 正式数据包构建
→ SQLite/CSV/JSON/Excel QA
→ N3/N4 用户节点
→ Git 标签和 Release
```

V1 证明以下机制有效：来源 ID、候选/正式分离、解释关系双来源、hold/gap、Reviewer 独立、差量返修、单线程整合、自动 QA、节点式 Git、用户只做全局节点。

V1 也证明以下做法应当淘汰：所有小任务都做 FULL 大包、多份过程文档手抄同一数字、把共享脚本 pass 当作语义 pass、在内容卡旁路 hold、用低置信度掩盖无来源、把 CSV/Excel/JSON分别维护为事实源。

详细证据见 `project/audits/research/V1_工作流程审计摘要.md`。

## 4. 审计发现与流程优化

### 4.1 从“阶段建设”改为“变更集维护”

发布后不再为一条数据重跑 N1—N4。每次维护建立一个 change set，只包含：

- 本次新增/修改的候选记录；
- 复用或新增的来源；
- Reviewer 结论；
- SQLite 迁移；
- 受影响导出物；
- QA 和版本建议。

### 4.2 从“全包文档”改为风险分级

- 外部低风险机械任务使用 `LITE`：任务说明、主体成果、一个合并 HANDOFF。
- OCR、解释性研究、批量迁移、版权风险或 Schema 相关任务使用 `FULL`。
- Codex内部单条纠错无需制造外部包，但必须保留任务 ID、变更理由、来源、Reviewer、迁移和 QA 记录。

### 4.3 从“人工统计”改为机器报告

所有行数、状态分布、来源覆盖、ID 数量和导出计数由脚本从最终 SQLite 或候选 CSV 生成。README、HANDOFF、CHANGELOG 只引用必要结果，不复制整套统计表。

### 4.4 从“V1 专用脚本”改为通用流水线

当前 `build_v1_candidate.py` 与 `validate_v1_candidate.py` 是 v1.0.0 快照工具。未来增量需建立：

```text
apply_migration
→ validate_master
→ export_from_sqlite
→ validate_exports
→ build_release_manifest
```

在这套工具完成前，不得通过手工编辑导出物来宣称正式数据已更新。

## 5. 当前统一数据工作流

### 5.1 第一步：分类

收到请求后，维护 AI 必须将其归入一种或多种类型：

- A 新增来源；
- B 新增作家；
- C 新增作品；
- D 补充已有实体事实；
- E 新增关系；
- F 补证 hold；
- G 修改已发布数据；
- H 批量新增。

一项任务可以组合，例如“新增作家 + 三部作品 + 五项来源”，但必须在任务卡中列出每个子变更及共同边界。

### 5.2 第二步：查重与影响分析

在研究前检查：

- 来源：DOI、ISBN+版次、稳定 URL、规范化题名+作者+年份；
- 实体：中文名、原文名、别名、类型、上下文；
- 关系：规范化三元组 `subject_id + relation_type + object_id`；
- 事实：`subject_id + fact_field + value_text`；
- 已知 hold/gap/disputed；
- 是否影响 Schema、正式 ID、核心范围、版权或公开边界。

查重结果必须是 `reuse / new / possible_duplicate / keep_separate / conflict` 之一。字符串相似不能自动合并。

### 5.3 第三步：建立来源基础

复用已有 `SRC` 或生成来源候选。Worker 不分配正式 `SRC`；Data Integrator 在审核后分配。没有合格来源时，任务保持 discovery/candidate/gap，不继续制造正式数据。

### 5.4 第四步：生成最小候选变更集

候选必须明确：对象、字段或三元组、来源、证据说明、置信度、争议状态、任务 ID。不要复制未受影响的全库记录。

### 5.5 第五步：Worker 自检

运行标准解析、ID、枚举、引用、来源、URL记录和安全边界检查。Worker 只能写“自检完成，等待 Reviewer/Codex”，不能写最终 pass。

### 5.6 第六步：独立 Reviewer

Reviewer 检查：来源身份、对象层级、证据是否直接支持、来源是否独立、表述是否越权、状态是否正确。结论只允许 `pass / revise / reject`。

### 5.7 第七步：正式整合

只有 Data Integrator 可以：

- 分配正式 ID；
- 决定已批准的实体复用/合并；
- 通过迁移写 SQLite；
- 更新迁移日志；
- 生成导出物。

### 5.8 第八步：QA、版本和发布

先验证主库，再重建导出，再验证导出一致性。根据变化决定 Patch/Minor/Major，更新 CHANGELOG。正式 tag/Release 属用户版本节点；没有明确发布授权时，停在已验证的发布候选。

## 6. 来源管理规范（SOP-A）

### 6.1 查重顺序

1. DOI / Handle / ARK / OCLC 等持久标识；
2. ISBN + 版次/译本；
3. 规范化 canonical URL；
4. 题名 + 作者/机构 + 年份；
5. 物理/数字版本差异。

同一论文的索引页、DOI 页、期刊页和 PDF 是一个来源的多个入口，不分配多个 `SRC`。不同版次、译本或实质不同的出版物分别编号。

### 6.2 最低书目信息

正式来源至少应保存：

- source_id；
- 完整题名；
- 作者/编者/机构；
- 出版载体或机构；
- 年份（可确认时）；
- 类型、语言、来源等级；
- DOI/ISBN/持久标识/稳定 URL（存在时）；
- 页面标题、访问日期和访问状态（网络来源）；
- public_content_scope、local_asset_status 和版权说明；
- 任务 ID 与核验责任人。

### 6.3 来源等级

| 等级 | 典型来源 | 允许用途 |
|---|---|---|
| A | 原著、学术专著、同行评议论文、合格学位论文、大学出版社研究 | 核心事实、作品级研究、解释性判断 |
| B | 国家/大学图书馆、出版社、基金会、大学研究中心、官方目录 | 书目、人物、出版和背景事实 |
| C | 权威媒体、专业书评、可靠访谈、会议摘要线索 | 补充背景或观点线索；一般不能独立承担高强度解释 |
| D | 普通网页、聚合页、百科、搜索结果 | discovery only，不进入正式事实/解释关系 |

等级按实际可核验对象决定。学术平台上的索引或摘要不会自动成为 A；出版社作者聚合页不会自动成为具体作品书目页。

### 6.4 OCR 与公开边界

- 只在研究需要时做 L0/L1/L2；L3 全文 OCR 必须任务卡明确授权。
- 原书、PDF、EPUB、整书 OCR、完整文字层、私有批注和凭据只留本地。
- 公开仓库只保存合规元数据、释义、引用信息和必要短摘录。
- 被登录、验证码、403、付费墙拦截时不绕过；记录 access blocked 并寻找合法替代。

### 6.5 正式登记

Reviewer 通过后，由 Integrator 在 SQLite `sources` 分配下一个未使用 `SRC-XXXX`。ID 永不复用。若来源只作线索，进入 source hold/discovery，而不是正式来源表。

现有 `data/catalog/SOURCE_REGISTRY.csv` 是 V1 建设期正式来源目录和公开发布记录。完成第 14.2 节主库迁移后，`sources` 表成为来源记录的正式写入点，`SOURCE_REGISTRY.csv` 改由主库导出，不再与 SQLite 双向人工维护。迁移完成前不得在两处分别分配 SRC；若必须处理增量，应先完成基线迁移。

## 7. 实体新增 SOP

### SOP-B：新增作家

1. 查中文名、原文名、异体拼写、重音差异和同名人物。
2. 判断类型必须为 `author`；不要把编辑、译者、导演自动当作 author。
3. 至少取得一项 A/B 权威人物来源支持身份和基础事实；若升级为核心作家，至少两项可靠来源。
4. 候选字段至少包括：规范中文名候选、原文名、别名/译名、语言、国家或地区、生卒年、来源、冲突说明。
5. 生卒年、国籍、出生地分别作为原子事实，不因常识一起填充。
6. 作品关系使用 `CREATED`，需具体作品和直接书目/权威来源。
7. 文学运动使用 `ASSOCIATED_WITH_MOVEMENT`，属解释性关系，原则上双独立来源。
8. 当前 Schema 没有 `BORN_IN`。出生地先存为有来源的 `birth_place` 事实；不得自行新增关系词。确需结构关系时提交兼容性提案。
9. Reviewer 通过后由 Integrator 分配 `V1-ENT` 或后续版本稳定实体 ID，并建立来源事实和作品关系。

### SOP-C：新增作品

1. 查重时区分 `work / collection / edition / adaptation`，同名不同层必须分开。
2. 保存中文名、原文名、作者、实体类型、语言、体裁、书目时间和版本说明。
3. 作者关系 `author → CREATED → work/collection` 可由一个合格直接来源确认。
4. 出版年份是事实字段，不使用当前 Schema 不存在的 `PUBLISHED_IN`；写作年、杂志首刊年、首个书版年、修订版年必须拆成不同字段。
5. 体裁可作为事实；如果未来需要结构化体裁实体，先走 Schema 兼容程序。
6. 主题 `EXPLORES_THEME` 是解释性关系，原则上需要两项独立可靠来源。
7. 场景地点 `SET_IN` 需要原作或合格来源明确支持，不从作者籍贯、标题或常识推断。
8. 历史事件 `BASED_ON_EVENT` 必须是 `work → event`，且至少一项 A 级来源直接表达取材、重述、虚构化或以该事件为基础；标题并置不能单独成立。
9. 每部核心作品至少完整书目信息和一项作品级研究依据；短篇级材料不能关闭作品集级缺口。
10. 内容卡只引用已准入事实；hold/gap/research note 放入独立栏目。

## 8. 事实与关系新增 SOP

### SOP-D：补充已有实体事实

适用于出生年、出版信息、城市、简介、原文名、来源补充等。

1. 锁定正式 subject_id 和目标 fact_field。
2. 检查是否已有相同、不同或冲突值。
3. 只处理目标字段；不重新跑无关 OCR、实体研究或策展覆盖。
4. 一个字段只表达一个语义；组合年份或组合观点必须拆分。
5. 直接事实使用一项合格且明确显示该值的来源即可；来源没显示该值时，不能靠 `low` 置信度保留。
6. 冲突值不静默覆盖：建立 disputed 候选，列出双方来源和差异。
7. Reviewer 核对后用迁移新增/修正事实及关联来源。
8. 运行全局外键/引用 QA 和受影响对象回归检查。

### SOP-E：新增关系

当前正式关系词只能来自 Schema 0.4：

`CREATED`、`CONTAINS_WORK`、`EDITION_OF`、`TRANSLATION_OF`、`ADAPTED_FROM`、`DIRECTED`、`SET_IN`、`ASSOCIATED_WITH_PLACE`、`ASSOCIATED_WITH_MOVEMENT`、`EXPLORES_THEME`、`RESPONDS_TO_WORK`、`INFLUENCED_BY`、`BASED_ON_EVENT`、`APPEARS_IN`。

#### 事实/结构型关系

| 关系 | 最低证据 |
|---|---|
| `CREATED` | 一项明确作者—作品的合格来源 |
| `CONTAINS_WORK` | 权威目录、原书目录或机构书目直接显示收录 |
| `EDITION_OF` / `TRANSLATION_OF` | 具体版本书目直接说明；不得只凭题名 |
| `ADAPTED_FROM` / `DIRECTED` | 官方改编资料、片目或合格研究来源 |
| `SET_IN` | 原作或合格来源直接说明场景 |
| `ASSOCIATED_WITH_PLACE` | 具体、可说明关联性质的人物/作品背景事实；模糊关联转 hold |
| `BASED_ON_EVENT` | 至少一项 A 级直接表达，且端点仅 work→event |
| `APPEARS_IN` | 一项合格来源直接识别人物属于该作品；端点仅 character→work；不保存 inverse |

#### 解释型关系

`ASSOCIATED_WITH_MOVEMENT`、`EXPLORES_THEME`、`RESPONDS_TO_WORK`、`INFLUENCED_BY` 原则上需要两项独立可靠来源。每项来源必须实际支持同一规范化三元组，而不是分别支持复合描述的不同部分。

#### 关系处理步骤

1. 验证两端实体存在且类型与 Schema 兼容。
2. 查重规范化三元组。
3. 区分 direct（含 `APPEARS_IN`）/ interpretive / special (`BASED_ON_EVENT`)。
4. 对每项证据记录来源 ID、题名、证据说明和独立来源键。
5. 单来源解释关系进入 `hold_needs_second_source`。
6. Reviewer 判断证据与三元组是否同层、同义和独立。
7. Integrator 分配正式 relationship_id，写关系、证据和关系—来源关联表。

不得使用当前 Schema 不存在的 `PUBLISHED_IN`、`BORN_IN`、`PARTICIPATED_IN_EVENT`、`RESPONDS_TO_EVENT` 等旧试行关系词。需要时提交提案，不得临时写入正式表。

## 9. hold 补证 SOP（SOP-F）

```text
hold_needs_second_source
→ 读取原三元组与第一来源
→ 查找真正独立、同对象层级的第二来源
→ 记录来源候选和独立性依据
→ Reviewer 审核
→ verified / 继续 hold / disputed / rejected
```

### 9.1 独立来源判断

以下不算第二独立来源：

- 同一论文的 DOI 页、期刊页、PDF、索引页；
- 同一来源的标题和正文；
- 聚合页与其指向的原记录；
- 同一通讯稿的转载；
- 同一作者同一研究成果的不同格式；
- 只重复引用第一来源、没有独立判断的网页。

### 9.2 升级条件

第二来源必须：对象层级一致、三元组一致、直接支持关键判断、来源身份可核验、与第一来源独立。满足后 Reviewer 才可建议 verified；Integrator 执行状态迁移。找不到时保持 hold，不重置已批准的访问预算，不为完成任务强行升级。

## 10. 已发布数据修改 SOP（SOP-G）

### 10.1 变更分类

- 纠错：原数据错误、错别字、URL、年份、类型或来源回指错误；
- 补充：增加新来源、证据、别名、事实或卡片说明；
- 重构：实体拆分/合并、ID变化、Schema或导出契约变化。

### 10.2 必须记录

- 修改对象与旧值；
- 新值和理由；
- 新旧来源；
- Reviewer；
- 迁移脚本/变更集 ID；
- 影响的关系、事实、卡片和导出；
- 版本号判断。

### 10.3 禁止静默覆盖

已发布记录不得直接在 Excel、JSON、CSV 或 SQLite GUI 中无记录修改。纠错必须通过可复核迁移；Git 保存迁移、报告和导出差异。实体合并/拆分必须保留旧 ID 映射或重定向，不能让旧引用失效而无说明。

### 10.4 冲突处理

新来源与已发布值冲突时，先进入 `disputed`：保留原值、候选新值、双方来源和争议说明。只有证据足够且 Reviewer 通过后才迁移；重大历史解释或政策变化由 PM 决定是否提交 USER。

## 11. 批量数据新增 SOP（SOP-H）

适用于多位作家、多部作品、新地区或专题。出现下列任一情形即建议批处理：共享来源较多、实体交叉多、预计新增关系较多、涉及覆盖平衡、需要统一 OCR/研究口径。数量只是提示，不是硬阈值；3 位作家或约 10 部作品通常应分 batch。

### 11.1 分批原则

- 每批 2—3 位作家、一个明确地区/专题或可独立审核的一组来源；
- 同一共享实体/正式 ID 域只允许一名 Integrator 写；
- Worker 可按独立来源域并行，但不能并行修改同一候选表；
- Reviewer 不审核自己的 Worker 输出；
- 上一批的 Schema/规范化决定先固化，再启动依赖批次。

### 11.2 批量流程

1. PM 生成 batch matrix 和固定范围。
2. 先全局来源/实体查重，再分发子批次。
3. Worker 用相同 Schema、枚举和模板生产候选。
4. 每批机械 QA + 交叉 Reviewer。
5. 返修按差量单执行。
6. PM 汇总跨批次重复、冲突和 coverage。
7. Data Integrator 按一个有序队列写 SQLite。
8. 全部批次后只做一次全量导出、覆盖审计和版本候选。

### 11.3 为什么整合必须单线程

正式 ID、实体合并、关系去重和迁移顺序彼此依赖。并行写主库会产生重复 ID、不同合并决定和导出漂移。并行只用于独立研究与审核，正式数据写入永远串行。

## 12. 数据准入标准

| 数据类型 | 最低来源要求 | 是否需 Reviewer | 是否可单来源确认 | 证据不足处理 |
|---|---|---:|---:|---|
| 来源书目记录 | 具体来源对象；A/B 机构页、原出版物或权威目录 | 是 | 是 | discovery/source hold |
| 作家身份与基础信息 | 一项直接 A/B；核心作家至少两项可靠来源 | 是 | 普通基础事实可 | candidate/disputed |
| 作品书目信息 | 原书、出版社、图书馆或具体权威记录 | 是 | 是 | gap/hold |
| 直接原子事实 | 一项明确显示该值的合格来源 | 是 | 是 | candidate/删除/gap |
| 内容卡事实陈述 | 每个事实有正式来源；只消费已准入事实 | 是 | 依事实类型 | 移入研究说明/hold |
| 结构型关系 | 一项直接、对象层级匹配的合格来源 | 是 | 是 | candidate/hold |
| `SET_IN` | 原作或合格来源明确说明 | 是 | 是 | hold/删除 |
| `BASED_ON_EVENT` | 至少一项 A 级直接表达 work→event | 是 | 可，但必须有 A 级直接证据 | pending/hold |
| `APPEARS_IN` | 一项合格直接来源，且人物与作品身份无歧义 | 是，逐条审核 | 是 | candidate/hold/reject |
| 解释型关系 | 原作/A级/合格研究；原则上两项独立来源 | 是，重点语义审核 | 否 | hold_needs_second_source |
| 实体合并/别名 | 类型兼容且有权威同一性依据 | 是，Integrator 决定 | 简单精确同一可 | keep_separate/unclear |
| hold 升级 | 新增真正独立、同层级、同三元组来源 | 是 | 否 | 继续 hold/disputed/rejected |
| 已发布数据纠错 | 与数据类型相匹配的新证据和迁移记录 | 是 | 依数据类型 | disputed/不修改 |

通用禁止：AI 自身知识不是来源；搜索摘要不是来源；D 级普通网页不能作为正式文学解释唯一依据；没有 source_id 与 source_title 的内容不进入正式事实/关系；冲突必须显式保留。

## 13. AI / Reviewer / USER 权限

| 角色 | 可以 | 不得 |
|---|---|---|
| Worker AI | OCR、来源整理、合法网络研究、候选实体/事实/关系、问题标记、机械自检 | 审核自己、分配正式 ID、把候选改正式、决定争议关系、改 Schema/章程/TASKS/主库、宣布节点 pass、操作 Git |
| Reviewer AI | 核对来源身份、证据强度、对象层级、语义、独立来源、争议；给 pass/revise/reject | 直接覆盖 Worker 文件、分配正式 ID、写主库、为完成数量降低门槛 |
| Data Integrator | 正式 ID、实体复用/已批准合并、迁移、SQLite、导出、技术 QA | 接收未通过 Reviewer 的数据、静默改已发布数据、私自改变 Schema |
| Project Manager | 分类、派单、范围、门禁、返修、决策记录、版本建议、Git候选、用户节点材料 | 越过用户改变使命/政策/重大 Schema/正式发布；未经授权改章程 |
| USER | 项目定位、重大范围、Schema重大/不兼容变化、数据政策、公开与版权高风险、正式版本节点 | 不需要逐条审核普通事实、OCR、URL修复、hold补证或常规纠错 |

如果同一 AI 兼任多个角色，必须在流程上分离：先以 Worker 身份交候选并结束，再以独立上下文/明确 Reviewer 身份复核；高风险解释关系优先使用不同 Agent。

## 14. SQLite 与导出规则

### 14.1 单一主数据

未来增量的唯一正式写入路径为：

```text
候选与 Reviewer 结论
→ 版本化迁移脚本
→ SQLite 主库
→ 导出构建脚本
→ CSV / JSON / Excel / 网站数据
```

禁止：

- 人工修改 Excel 后当作主数据；
- 人工修改 JSON/CSV 后不回写 SQLite；
- 页面代码硬编码文学事实；
- 分别维护多套数据；
- 用导出物反向覆盖主库，除非经过正式导入迁移与审核。

### 14.2 V1.0.0 到长期主库的过渡

当前正式快照位于 `data/staging/v1_candidate/V1_CANDIDATE.sqlite`，但目录名和构建脚本带有建设期遗留。第一次增量前必须：

1. 从 `v1.0.0` 标签核验 SQLite 哈希和 integrity；
2. 以只读复制/迁移建立 `data/master/` 正式基线；
3. 登记基线版本和来源 commit；
4. 建立迁移序号与已执行迁移表；
5. 建立 SQLite→CSV/JSON/Excel 的可重复导出；
6. 验证新导出与 v1.0.0 逻辑内容一致；
7. 才开始第一项增量迁移。

原 `data/staging/v1_candidate/` 不原地覆写，作为 v1.0.0 历史快照保留。

### 14.3 迁移规则

- 每个变更集一个有序迁移；
- 在事务中执行，失败必须回滚；
- 先验证前置版本、目标 ID和查重条件；
- 正式 ID按各序列下一个未使用值分配，删除后不复用；
- 实体合并保留 mapping/redirect；
- 迁移完成记录 task_id、reviewer、version、timestamp 和校验结果；
- 导出目录按版本生成，不在旧版本目录原地改写。

## 15. QA 与自动检查

能用脚本验证的，不依赖 AI “感觉正确”。每次正式增量至少执行：

1. 所有主键唯一，格式合法，不复用旧 ID；
2. SQLite 外键启用且引用完整；
3. 关系主体/客体存在且类型符合 Schema；
4. source_id 存在；
5. source_title 存在并与来源表一致；
6. relation_type、entity_type、状态、置信度等枚举合法；
7. URL 语法合法，并有核验状态和日期；
8. `PRAGMA integrity_check = ok`；
9. `PRAGMA foreign_key_check` 为 0；
10. CSV 可由标准库解析，行列稳定，无匿名列；
11. Excel 工作表数/表名符合导出清单，公式错误为 0；
12. JSON 可解析，`schema_version` 与 JSON Schema/发布版本一致；
13. 无 orphan evidence、fact source、card fact、card source；
14. 无 broken relation；
15. 统计数字从 SQLite 自动生成；
16. CSV/JSON/Excel 与 SQLite 的行数、主键集合和规范化内容一致；
17. 公开包无 PDF/EPUB、原书、整书 OCR、inputs、credentials、Cookie、环境配置、缓存或 local_only；
18. `git diff --check`、staged 文件白名单、无意外删除和敏感信息扫描通过。

语义 Reviewer 另检查：来源实际对象、来源等级、证据对象层级、原子事实、独立来源、作者级/作品级边界、hold是否旁路、冲突是否保留。

### 15.1 验证器分层

- `validate_master`：动态验证任何版本的不变量，不硬编码计数；
- `validate_exports`：SQLite 对 CSV/JSON/Excel 一致性；
- `validate_public_boundary`：禁止文件与敏感信息；
- `validate_release_snapshot`：针对特定标签的固定计数和关键回归。

当前 `validate_v1_candidate.py` 属最后一类，不能代替前三类。

### 15.2 当前工具入口

```text
python3 scripts/validate_master.py data/master/V1_MASTER.sqlite
python3 scripts/apply_migration.py data/master/V1_MASTER.sqlite data/master/migrations/0001_example.sql --task-id <TASK-ID> --reviewer <REVIEWER>
python3 scripts/export_from_sqlite.py data/master/V1_MASTER.sqlite data/exports/<VERSION> --version <VERSION>
```

迁移文件必须先经 Reviewer；导出目录默认不得覆盖已有内容，只有明确的重建操作才使用 `--force`。`export_from_sqlite.py` 生成 CSV、JSON、XLSX 和 MANIFEST，且固定 XLSX ZIP 元数据以保证同一 SQLite 输入的重复构建字节一致。

## 16. 版本与 Git 规则

### 16.1 Patch：`1.0.x`

用于不改变数据结构和公开契约的纠错或维护：

- 错字、元数据纠错；
- URL 修复；
- 给既有正式记录补来源或证据；
- 不新增正式关系的 hold 研究记录更新；
- 小范围卡片措辞修正。

若 hold 升级后新增一条正式关系，属于 Minor，不是 Patch。

### 16.2 Minor：`1.x.0`

用于向后兼容的数据扩展：

- 新增作家、作品或其他实体；
- 新增正式关系；
- V1.1 数据扩展；
- 向后兼容的新字段、表或关系词；
- 新专题批次但不改变项目使命。

兼容性 Schema 加法仍需决策记录；是否提交 USER 取决于是否属于章程要求的重大 Schema/数据政策变化。正式发布节点始终由 USER 批准。

### 16.3 Major：`x.0.0`

用于：

- 不兼容 Schema；
- ID 语义或导出契约破坏；
- 项目定位/核心范围重大变化；
- 主数据模型重大重构；
- 需要消费者迁移的删除或改名。

必须由 USER 决定。

### 16.4 Git 流程

1. 从最新 `origin/main` 建立 `codex/` 分支；
2. 只暂存本变更集明确文件，不使用 `git add .`；
3. 提交前跑完整 QA、公开边界和 diff 审查；
4. 提交正文记录 task、Agent、验证和已知问题；
5. 使用普通安全推送和 PR，不 force、不改历史、不绕过 required checks；
6. 合并后由发布节点创建语义化标签；
7. Release 使用仓库内审核过的发布说明；
8. 没有 USER 正式发布批准时，不创建正式 tag/Release。

普通研究/返修可本地累积或进入工作分支；一个 release 聚合相关变更，不为每个微小过程文件创建正式版本。

## 17. 常见错误与防错规则

| 错误 | 防错规则 |
|---|---|
| 搜索摘要当来源 | 必须打开原页；摘要只作 discovery |
| 索引/聚合页当论文 | 核验具体作者、题名、载体、年份、标识符 |
| 页面对象层级错配 | 证据对象必须与目标实体层级一致 |
| 同一论文计成两源 | 用 independent_source_key 去重底层研究成果 |
| CSV 逗号错列 | 标准 csv writer + parse round-trip |
| 自创枚举 | 从 Schema/任务卡读取允许值并自动断言 |
| 复合年份/观点一行 | 原子化拆行 |
| 低置信度掩盖无来源 | 无直接来源则 candidate/hold/gap，不入正式 |
| 同名实体误合并 | 同名默认不等同；先核类型与权威同一性 |
| 作者观点下推作品 | 必须有作品级指向 |
| hold 在卡片确定化 | 卡片只消费准入视图；hold用来源归属措辞 |
| Worker 自己 pass | Worker只自检；Reviewer/Codex给 verdict |
| 手工维护统计 | 机器生成一次，文档引用 |
| 导出物不同步 | 只改 SQLite并全量重建导出 |
| 版本发布静默覆盖 | 迁移+CHANGELOG+SemVer+Git tag |
