## 1. 性质、使命与成果边界

项目面向中文读者，建设来源可追溯、研究判断可复核、可持续扩展的拉丁美洲文学内容数据库，并以此支撑文学地图、时间线、关系网络、主题探索、阅读路径和数字展览。

项目不是作家百科或文学史文字的机械搬运。Research Data 负责保存规范实体、事实、关系、来源与证据；Curation Data 负责读者向策展；Web Data 和网站负责可解释的展示。网站不得另行维护一套研究事实。

`V1 / V2 / V3` 只表示项目阶段，不表示 Research Data、Schema 或 Web Product 版本。未来能力必须保持研究证据、版权和公开边界的连续性。

## 2. 文件权威层级与文档分类

按以下层级处理冲突：

1. USER 当前明确指示；

文档按职责分类：

| 类别 | 权威入口 | 规则 |
| --- | --- | --- |
| 活跃稳定规则 | 本章程、`docs/`、稳定产品说明、`project/ai/AI_COLLABORATION_GUIDE.md` | 说明长期方法和不变量，不承载每日进度 |

`project/internal/` 整体为本地工作区，不是公开协作或发布入口。动态任务只能以 `project/internal/TASKS.md` 为准；动态决策以 `project/internal/DECISIONS.md` 为准。活动文档只链接稳定入口或当前公开事实，不复制另一套实时状态。

## 4. 研究、数据与版权原则

1. 来源先于事实；正式研究事实必须回到可识别且合法可访问的来源对象。
2. 候选先于正式；AI 产出经过独立复核后才能进入正式数据。
3. SQLite 是 Research Data 的唯一正式写入主库；CSV、JSON、Excel 和 Web Data 从明确输入重建。
4. Research、evidence、Curation、reader projection 和 Web Data 分层保存，不互相伪装。
5. 解释性关系须有对象层级相符的直接证据；不能确认时保留 `hold`、`disputed` 或 `research_gap`。
6. 不凭常识补写，不把作者观点自动下推到作品，不把出生地或短暂居留自动扩大为文学关系，不为虚构空间伪造现实坐标。
7. 原始书籍、扫描件、未获授权全文、私有批注、账号信息、Cookie 和密钥不得进入公开仓库。
8. 公开内容优先使用释义、书目信息、来源题名和必要短引文，并遵守第三方版权及许可边界。

## 5. 工作流与质量门禁

标准链路为：

```text
来源登记 → 候选实体/事实/关系 → Worker 自检
→ 独立 Reviewer → 版本化 SQLite 迁移
→ 导出与不变量 QA → Curation → Web Data → 页面验证
```

每项可交付工作必须有明确范围、输入、输出、责任人、证据和验证记录。任何不确定项都 fail-closed；不能用写作、数量或前端代码掩盖研究缺口。适用的数据库、导出、链接、敏感信息、公开边界、构建和浏览器检查必须在交付前完成。

## 6. Git、分支与 PR 收口

- 在 `codex/` 分支或 USER 指定分支上完成范围清晰的变更，提交说明真实内容。
- 同一范围已有 PR 时，继续使用其分支并在同一 PR 内闭合治理、文档、测试和审计修订，不另建 PR。
- 使用追加提交；不强制推送、不 squash 他人提交、不改写历史。
- 治理整理不得顺手修改无关研究数据或新增未经请求的 reader-facing 内容。
- 合并前检查 diff、活动链接、敏感信息、归档完整性、内部文件追踪状态及适用的数据/Schema/Web 构建。

## 7. 版本规则与 Public Release Gate

Research Data、Research Schema、Web Data schema 和 Web Product 各自编号，任何一层不因另一层变化而自动升级。路径迁移、文档整理、构建/验证修复或无读者向内容的 Research-only 投影不构成 Data/Schema 版本升级；只有实质内容、结构或公开契约变化才提出对应升级。

- Web Product 只有在没有新增 reader-facing 内容的治理、文档、修复或 Research-only 投影变化时使用 patch。
- 新增读者可见内容、页面类型或实质能力时使用 minor；破坏公共契约或正式公开发布时才考虑 major。
- 公开预览不等于正式发布。未批准的 `user_review`、`hold`、研究缺口和工作稿不得进入公开包。
- Public Release 是独立用户门禁：USER 必须明确开启并批准，且研究、策展、Web Data、版权、公开边界、部署、回滚和 QA 证据齐全后，才可创建正式 Tag、GitHub Release 或生产部署。
