# 拉丁美洲文学地图：外部 AI 任务分工与交接手册

版本：0.5.4

用途：将本文件与对应资料、任务模板一起交给其他 AI，即可直接开始基础工作

> 所有外部 AI 开工前必须完整阅读仓库根目录 `project/governance/PROJECT_CHARTER.md`。该文件是用户锁定的最高项目总章程，任何外部 AI 均不得修改、移动、重命名或删除。

## 1. 这份手册解决什么问题

本项目把高重复、低判断风险、消耗大量上下文的资料处理交给其他 AI，把有限的 Codex 用量保留给知识模型、证据判断、关系审核、数据库整合和项目收口。

外部 AI 不是独立决定项目方向的研究者，而是领取标准任务包的 Worker。它的成果必须让一个没有参与对话的 Codex 能够理解、复核和继续处理。

## 2. 总体职责分配

| 工作 | 其他 AI | Codex | 用户 |
|---|---|---|---|
| 文件清单、格式和页数盘点 | 主做 | 抽检、编号 | 提供资料 |
| 版权页、目录和任务指定内容 OCR | 主做 | 设定范围、抽检 | 无需逐项审核 |
| Markdown 结构整理；任务卡要求时增加页码锚定 | 主做 | 退回不合格结果 | 无需逐项审核 |
| 来源档案和书目信息初填 | 主做 | 分配正式来源 ID、解决冲突 | 无需逐项审核 |
| 作家名、作品名、地点等候选抽取 | 主做 | 规范化并确认 | 无需逐项审核 |
| 重复项、别名和译名候选检测 | 主做 | 决定是否合并 | 无需逐项审核 |
| 文学影响、主题和争议性关系 | 只提供候选和定位 | 主做判断与复核 | N2/N3 看代表性结果 |
| Schema、SQLite 和数据迁移 | 不做 | 主做 | N2 审核 |
| 作家卡、作品卡和策展文本 | 可提供事实素材 | 主写或最终审核 | N3 审核 |
| Git、GitHub、版本和公开边界 | 不做 | 在预定义节点主做自动审计、提交和推送 | N3/N4 仍审核候选版与正式发布 |

## 3. 外部 AI 的统一硬规则

每次把任务交给外部 AI 时，都必须同时提供：

1. 一个唯一任务 ID；
2. 明确的输入文件；
3. 允许处理的来源、文件、内容单元或字段；页码/章节仅在确有必要时填写；
4. 应生成的文件清单；
5. `project/governance/PROJECT_CHARTER.md`；
6. 本手册和 `docs/data/数据新增与版本维护操作手册.md`；阶段 0 历史规范仅从 `project/archive/v1-foundation/阶段0_研究与数据规范.md` 追溯；
7. 对应的 `templates/external-ai/` 模板。

外部 AI 必须遵守：

- 只处理当前任务，不擅自扩展到其他文件、章节或研究问题；
- 不修改、移动、重命名或删除 `project/governance/PROJECT_CHARTER.md`；
- 不修改原始文件，不改 `project/tasks/TASKS.md`，不写主数据库，不操作 GitHub；
- 不把用户资料上传到公开链接；
- 不用常识填补 OCR 缺字，不编造出版信息或来源；
- 不把候选结论写成已确认事实；
- 每个事实或候选项至少保存来源 ID 和来源题名；书籍到书名、论文到论文名、网页到页面标题和 URL 即满足最低要求；
- 页码、章节、电子位置和短摘录只作为可选增强项，不要求逐页补录；
- 无法确认的内容进入 `ISSUES.md`；
- 交付必须是完整文件包，不能只有聊天窗口中的总结；
- 完成后生成 `HANDOFF.md`，明确告诉 Codex 下一步该做什么。

## 4. 任务包结构：LITE 与 FULL

任务卡必须声明 `package_profile`。

任务卡还应声明 `execution_scope: single|milestone_bundle`。默认优先使用 `milestone_bundle`：把 2—4 个相邻机械子任务合并执行，例如“来源级文本整理 + 候选实体抽取 + 覆盖统计”。只有输入、权限、数据写入方或验收门禁明显不同时才拆为独立任务。

### 4.1 LITE 轻量包

适用于 ID 回填、书目核对、覆盖统计、格式检查等低风险机械任务：

```text
<TASK-ID>_<任务主题>/
├── README.md
├── <主体成果.csv|md>
└── HANDOFF.md
```

`HANDOFF.md` 必须合并包含最终状态、机械 QA、问题、交付文件清单、公开边界和下一步。可以有多个主体成果，但不为凑文件数量创建重复过程文档。

### 4.2 FULL 完整包

适用于 OCR、研究抽取、关系审核、数据库迁移和高版权风险任务：

```text
<TASK-ID>_<任务主题>/
├── README.md
├── STATUS.md
├── MANIFEST.md
├── SOURCE_RECORD.md          # 来源建档任务
├── OCR.md                    # OCR 任务
├── ENTITY_CANDIDATES.csv     # 候选抽取任务
├── RELATION_CANDIDATES.csv   # 经任务卡允许时才生成
├── QA_REPORT.md
├── ISSUES.md
├── REVIEW.md                 # 独立 Reviewer 任务
└── HANDOFF.md
```

不要自行改名为“最终版”“整理结果2”“完整结果”等无法批量识别的名称。无论 LITE/FULL，都必须保留任务 ID、Agent、状态、QA、问题、HANDOFF 和文件清单信息。

## 5. 过程状态要求

FULL 任务至少在以下时间更新 `STATUS.md`；LITE 任务在 `HANDOFF.md` 中记录同等信息：

1. 开始时：记录 Agent、模型、任务理解、输入和预计步骤；
2. 完成约一半时：记录已完成范围、发现的问题和剩余工作；
3. 结束时：状态必须写 `done`、`blocked` 或 `failed`；
4. 任何需要用户/Codex决定时：写 `needs_input: yes`，说明具体问题和可选方案。

对于无法持续写文件的平台，可以在结束时补写过程时间线，但不得省略中间发现的问题。

## 6. 可直接分配给其他 AI 的任务类型

默认交付模式：A 文件清单、F 名称核对、G 书目网络核对使用 `LITE`；B 来源建档、C OCR、D OCR 质检、E 候选抽取使用 `FULL`。任务卡可以基于版权、规模或迁移风险提高为 FULL，但不得无理由把机械任务扩大为完整包。

### A. 文件接收与资料清单

适合：任何能读取文件名、PDF 元数据或截图的 AI。

输入：一批文件或文件目录。

执行步骤：

1. 逐个记录原文件名，不重命名原件；
2. 判断格式、文件大小、页数、是否有文字层和主要语言；
3. 初步识别题名、作者、译者和版本；
4. 标记重复文件、损坏文件、加密文件和疑似扫描件；
5. 建议后续处理为 L0/L1/L2/L3；
6. 标记可能含隐私、版权全文或其他敏感内容的文件。

必须交付：`SOURCE_MANIFEST.csv`、`QA_REPORT.md`、`ISSUES.md`、`HANDOFF.md`、`MANIFEST.md`。

禁止：阅读后自行做文学分析；给来源分配正式 `SRC-` 编号；公开上传文件。

验收：文件数量与输入一致；每个文件有处理建议；无法读取的文件明确列出。

### B. 单份来源建档

适合：OCR、文档阅读和书目整理能力较强的 AI。

输入：一个来源文件、任务 ID、Codex 分配的来源 ID。

执行步骤：

1. 定位封面、版权页、目录、参考文献和索引；
2. 抄录题名、作者/机构、译者、出版社、出版年、版次、ISBN/DOI；
3. 判断资料类型和语言；
4. 记录文件格式、页数、目录结构和最低引用方式（书名/论文名/网页标题与 URL）；
5. 按规范提出来源等级建议；
6. 记录版权和使用限制；
7. 对每个不确定字段给出页面依据和问题说明。

必须交付：`SOURCE_RECORD.md`、必要的指定页 OCR、`QA_REPORT.md`、`ISSUES.md`、`HANDOFF.md`。

禁止：根据网名或文件名猜出版社、年份、ISBN；把来源等级建议写成最终结论。

### C. OCR 与 Markdown 结构整理

适合：带 OCR、视觉识别或文档解析能力的 AI。

输入：一个文件、明确的来源或内容范围、OCR 层级；页码/章节可选。

执行步骤：

1. 先检查版式、栏数、脚注、表格和图片；
2. 只处理任务卡规定的范围；
3. 按来源和任务范围组织文本；只有任务卡特别要求时才在每页起始处写 `<!-- page: N -->`；
4. 保留标题、段落、列表、脚注和表格结构；
5. 无法辨认写 `[无法辨认]`；
6. 对专名、数字、年份、作品名和引文进行重点核对；
7. 按开头、中部、结尾抽样，并记录准确率和错误类型；
8. 删除重复页眉页脚时在 QA 中说明。

必须交付：`OCR.md`、`QA_REPORT.md`、`ISSUES.md`、`STATUS.md`、`HANDOFF.md`、`MANIFEST.md`。

禁止：总结或润色原文；把不清楚的词按语义补全；超出任务范围做整书 OCR。

### D. OCR 独立质检

适合：没有参与原 OCR 的第二个 AI。

输入：原文件、OCR.md、原 Worker 的 QA 报告。

执行步骤：

1. 核对任务规定的抽样页；
2. 检查漏段、错序、脚注、表格和乱码；任务卡要求页码锚点时再检查锚点；
3. 重点核对专名、年份、数字、作品名和短引文；
4. 判断错误是否影响研究使用；
5. 给出 `pass`、`revise` 或 `reject`；
6. 对每个问题写明文件、内容位置和建议；原页码只在现成可用时填写。

必须交付：`REVIEW.md`、独立 `QA_REPORT.md`、`HANDOFF.md`。

禁止：只写“整体不错”；直接覆盖原 Worker 文件；自行降低准确率门槛。

### E. 候选实体和明确事实抽取

适合：能读结构化文本并输出 CSV 的 AI。

输入：已通过 QA 的 OCR、来源 ID、试行词表。

允许抽取：明确出现的作家、作品、地点、机构、文学运动、事件、主题词、出版信息和可直接从句子确认的基础关系。

执行步骤：

1. 每个候选使用暂存 ID；
2. 保存规范名称候选、原文名称和原文中的别名；
3. 保存来源 ID 和来源题名；页码/章节和短证据为可选增强；
4. 标记置信度；
5. 同名不同人、译名冲突和指代不明进入问题清单；
6. 对影响、代表、回应等解释性关系只提出候选，不下最终结论。

必须交付：`ENTITY_CANDIDATES.csv`；任务卡允许时交付 `RELATION_CANDIDATES.csv`；以及 `QA_REPORT.md`、`ISSUES.md`、`HANDOFF.md`。

禁止：自行分配正式实体 ID；自行新建关系词；删除看似重复的候选；用训练知识补充 OCR 中没有的事实。

### F. 译名、别名和重复项候选核对

适合：表格处理、文本比对能力较强的 AI。

输入：候选实体表、来源记录和规范名称列。

执行步骤：

1. 归组拼写差异、重音差异、中文译名和原文名；
2. 标记“高度可能同一实体”“可能同一实体”“不可判断”；
3. 为每项给出来源依据和判断理由；
4. 单列同名异人风险；
5. 不执行删除或合并。

必须交付：候选对照表、`ISSUES.md`、`HANDOFF.md`。

禁止：无来源强行统一中文译名；仅凭字符串相似就认定同一实体。

### G. 书目与网络来源机械核对

适合：具备联网检索能力的 AI。

输入：待核对书目、允许访问的网站范围、来源 ID。

优先来源：出版社、图书馆、大学、DOI/Crossref 类权威目录、作家基金会。

执行步骤：

1. 核对题名、作者、出版年、出版社、ISBN/DOI；
2. 保存每个网页的标题、机构、URL 和访问日期；
3. 记录不同来源之间的冲突；
4. 不用普通电商页面覆盖权威书目；
5. 输出“已确认”“有冲突”“未找到”。

必须交付：书目核对表、URL 清单、`QA_REPORT.md`、`ISSUES.md`、`HANDOFF.md`。

禁止：使用搜索结果摘要代替打开页面；编造无法访问页面的内容；把普通网页作为文学解释唯一来源。

## 7. 保留给 Codex 的工作

以下工作不要交给基础 OCR/整理 AI：

- 未经用户明确授权不得修改 `project/governance/PROJECT_CHARTER.md`；获得授权后也只能由 Codex 按章程变更程序执行；
- 修改关键决策和用户审核节点；
- 设计、冻结或迁移 Schema；
- 分配正式来源 ID 和正式实体 ID；
- 判断文学影响、运动归属、主题解释和来源冲突；
- 决定候选实体是否合并；
- 把暂存成果写入 SQLite 主数据库；
- 生成跨来源作家卡、作品卡、主题说明和策展路径；
- 运行 V1 覆盖、关系、引用和一致性审计；
- 更新 CHANGELOG、决策记录、README、Git 和 GitHub；
- 在 N1—N4 向用户提交节点审核包。

把下面文字复制给其他 AI，并替换尖括号内容：

```text
你是“拉丁美洲文学地图”项目的外部 AI Worker。

任务 ID：<TASK-ID>
任务类型：<资料清单/来源建档/OCR/质检/候选抽取/译名核对/书目核对>

允许范围：<来源、文件、内容单元或字段；页码/章节可选>

禁止范围：不得修改 project/governance/PROJECT_CHARTER.md、原件、主数据库、project/tasks/TASKS.md 或 GitHub；不得扩大范围、公开上传资料或猜测缺字和来源。

你必须先阅读：
1. project/governance/PROJECT_CHARTER.md

4. 本任务目录 README.md

必须使用任务卡指定的 LITE 或 FULL 模板，返回完整任务目录，而不是只在聊天中总结。

过程要求：
- 不修改、移动、重命名或删除 project/governance/PROJECT_CHARTER.md；
- FULL 任务在开始、约 50% 和结束时更新 STATUS.md；LITE 任务在 HANDOFF 中记录简要时间线；
- 所有事实至少保留来源 ID 和来源题名；书籍到书名、论文到论文名、网页到页面标题和 URL 即可；
- 不要求逐页录入页码；已有页码可作为可选增强信息保留；
- 无法确认写入 ISSUES.md，不得猜测；
- 完成独立抽样和机械检查；FULL 填写 QA_REPORT.md，LITE 写入 HANDOFF；
- 最终填写 HANDOFF.md；FULL 另填 MANIFEST.md，LITE 在 HANDOFF 内列出文件；
- 终态只能写 done、blocked 或 failed。

本任务的特定交付物：<列出文件>
验收标准：<从任务卡复制>

完成后只需回复：任务状态、任务目录路径/下载文件、机械检查结果、HANDOFF.md 摘要。不要用聊天摘要替代文件交付。
```

## 9. 用户如何把成果交回 Codex

建议将每个任务目录整体压缩为 `<TASK-ID>.zip`，不要拆散文件，也不要只复制聊天内容。交回时可直接说：

```text
这是外部 AI 完成的 <TASK-ID> 任务包。请按阶段 0 规范进行：
1. 检查文件完整性和范围；
2. 读取 HANDOFF、QA 和 ISSUES；
3. 抽样复核成果；
4. 给出 pass/revise/reject；
5. 通过后更新 TASKS，并决定是否进入暂存数据或下一任务；
6. 只把可公开的项目文档和结构化摘要提交 GitHub，不上传原始书籍或整书 OCR。
```

## 10. Codex 汇总时的读取顺序

Codex 收到任务包后按以下顺序处理，以节约用量：

1. `README.md` 与 `HANDOFF.md`：确认范围、Agent、完成项、QA、问题和下一步；
2. FULL 任务再读 `STATUS.md`、`QA_REPORT.md`、`ISSUES.md`、`MANIFEST.md` 与 `REVIEW.md`；
3. 先查看机械检查结果；能自动验证的数量和结构不在对话中重新手工计算；
4. 最后才读取较大的 `OCR.md` 或 CSV，并优先抽样而不是从头重复处理。

## 11. 退回修订的标准指令

如果任务不合格，Codex 可以只给外部 AI 以下结构化返修单：

```text
任务 ID：<TASK-ID>
结论：revise / reject
必须修复：
1. <文件 + 行号/记录 ID/内容位置 + 问题>
2. <文件 + 行号/记录 ID/内容位置 + 问题>

保持不变：<已经通过的范围>
禁止新增：<不得扩大的范围>
重新验证：<记录、内容单元或检查项>
返修后更新：只更新受影响的主体成果和过程记录；不得为了同步而无关改写已通过文件。
```

## 12. 短启动提示词、里程碑任务包与单队列

完整要求只保留在任务卡。把任务交给当前外部 AI 时，优先使用以下短启动语：

```text
请执行任务 <TASK-ID>。
任务卡：<README 路径>
输入：<输入路径>
交付：<交付目录>

请先完整读取任务卡及其中引用的章程和规范，严格按 package_profile 交付，并在完成前运行机械检查。
完成后只回复：状态、交付目录、机械检查结果、HANDOFF 三行摘要。
```

当前只有一名外部 AI 执行方时，仍采用单任务队列，避免同一数据文件并发写入；但一张任务卡应尽量覆盖 2—4 个相邻机械子任务，并只生成一次 HANDOFF。Codex可以同时准备 Schema 或验收规则，但不得与外部 AI 并行写同一数据文件。更换供应方时，旧交付保持原署名和只读状态，新执行方必须在首次交付登记真实平台与模型。

Codex 默认只在以下关键门禁审计：

1. 文件结构、标准解析、ID/引用完整性和安全边界；
2. 来源身份、访问合法性和覆盖范围；
3. 代表性语义样本、冲突和越权推断；
4. 暂存、主数据库或发布准入。

Worker 已用共享脚本通过的逐条机械项目，Codex不重复全量计算；页码、章节和 locator 等可选增强项不作为返修理由。只有抽样失败时，才扩大到对应来源或对应字段的全量复核。

## 13. 推荐的第一轮外部 AI 任务

在 N1 通过并收到 5—10 份资料后，按以下顺序派发：

1. 一个 `EXT-CATALOG` 完成全部文件的接收清单；
2. Codex 分配正式来源 ID；
3. 按来源拆分 2—3 个建档任务；
4. 按来源拆分 2—3 个 L1 OCR 任务；
5. 用另一个 AI 对其中至少一个 OCR 包做独立质检；
6. Codex 只读取交接包和抽样内容，形成阶段 1 首批汇总；
7. 再为博尔赫斯和李斯佩克朵建立 N2 试点任务卡。

不要一开始就把全部资料交给一个 AI 做整书 OCR。小批次更容易发现格式和质量问题，也更方便差量返修和汇总；不再以逐页录入作为默认工作量。
