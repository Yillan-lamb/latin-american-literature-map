# 二、任务管理原则

## 2.1 任务采用“可验收成果包”拆分

不得把 V2_TASKS 拆成大量低价值机械步骤。

不建议：

```text
TASK-001 统计 place
TASK-002 新建 CSV
TASK-003 写字段
TASK-004 修改字段名
```

应按可独立验收的里程碑成果拆分，例如：

```text
V2-S1-001：完成 V2 网站数据适配审计
V2-S1-002：完成地图数据补充与 QA
V2-S2-001：建立 Curation Data Schema
```

一个正式任务原则上应包含：

- 任务 ID；
- 任务名称；
- 当前状态；
- 负责人；
- 上游依赖；
- 任务目标；
- 执行范围；
- 明确产物；
- 验收标准；
- 下游解锁条件；
- 是否需要 USER 审核。

---

## 2.2 任务状态

`project/tasks/V2_TASKS.md` 统一使用：

- `✅ DONE`：已完成并通过验收；
- `🔵 IN_PROGRESS`：当前正在执行；
- `⏳ READY`：依赖已满足，可以执行；
- `🔒 LOCKED`：因上游任务或用户节点未通过而锁定；
- `⚠️ REVISION`：验收未通过，需要差量返修；
- `👤 USER_REVIEW`：等待 USER 节点审核；
- `⛔ BLOCKED`：存在外部依赖或无法自主解决的问题。

任一时刻原则上只保留少量 `IN_PROGRESS` 任务，避免同时铺开多个阶段。

---

## 2.3 节点优先于任务

V2 的正式用户节点为：

- `V2-N1`：产品决策书批准；
- `V2-N2`：核心交互原型审核；
- `V2-N3`：完整测试站审核；
- `V2-N4`：正式公开发布。

本节记录 V2-N1 初始化时的节点顺序。当前节点、解锁状态和下一任务必须以 `project/tasks/V2_TASKS.md` 为准；不得将本节的历史 N2 表述当作实时状态。
