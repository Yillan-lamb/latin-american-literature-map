## 1. 修改原因

现行规则要求所有 GitHub 上传都由 USER 逐次明确触发。该规则能避免频繁提交，但随着 V1 进入多批次研究和数据整合阶段，会产生两个问题：

1. 已通过成果长期只在本地累积，GitHub 的公开历史落后于实际项目状态；
2. USER 需要重复发送“上传”指令，增加沟通成本，也容易错过适合冻结的里程碑。

本提案把上传触发方式改为“预先授权的关键节点自动发布”：普通任务与返修仍不上传；只有预定义的 V1 里程碑达到门禁后，Codex 才自动执行一次公开边界审计、里程碑提交和 GitHub 推送。

## 2. 旧规则与拟议新规则

### 旧规则

- 公开变更可以在本地累积；
- 只有 USER 逐次明确通知“上传”或“提交并上传”时，Codex 才能提交并推送；
- 每个外部任务完成后不自动操作 Git。

### 拟议新规则

- 普通任务、R0/R1 返修、单个来源补核和局部文档调整继续只在本地累积；
- 当本提案第 3 节列明的关键节点满足全部触发条件时，USER 无需再次发送“上传”指令，Codex 在同一验收轮次自动提交并推送可公开成果；
- 自动授权仅覆盖普通 `commit`、普通 `push` 和预定义标签；不覆盖 force push、删除分支/标签、历史改写、敏感材料公开或扩大项目范围；
- 任一停止条件出现时，自动流程立即终止，不以“已预授权”为由绕过安全门禁。

## 4. 不触发自动上传的事项

以下事项继续只在本地处理，不产生独立 GitHub 提交：

- 单个外部 AI 任务首次交付；
- R1/R2 差量返修；
- 单个来源、译名、事实或关系的补核；
- 尚未通过 Codex 门禁的候选包；
- 仍含阻塞问题的 OCR、研究或数据库包；
- 临时脚本、缓存、预览图和过程日志；
- 仅用于本地恢复、调试或人工比对的文件。

## 5. 每个自动节点的固定执行流程

1. **节点确认**：在 `project/tasks/TASKS.md` 中确认依赖和 Codex/user verdict 已满足，不以聊天中的“看起来完成”替代正式状态。
2. **远端检查**：读取当前分支、`origin/main` 和远端差异；只允许普通快进式推送。远端出现未知新提交或分叉时停止。
3. **公开白名单**：按明确文件名逐项暂存，不使用 `git add .`；对未跟踪目录逐项检查。
4. **安全审计**：检查敏感信息、大文件、版权材料、local_only 标记、缓存和未登记文件。
5. **项目验证**：运行适用的共享验证、CSV/SQLite/JSON 一致性检查、引用完整性、`git diff --check` 和版本号一致性检查。
6. **暂存区复核**：查看 staged 文件名、统计和 diff；出现无关删除、跨范围污染或异常生成物时停止。
7. **里程碑提交**：每个节点原则上只形成一个语义清楚的 milestone/release commit；提交正文写任务范围、验证结果、Agent 归属、已排除的本地材料和已知问题。
8. **普通推送**：禁止 force push、`--no-verify`、amend 或历史重写。默认把通过节点的提交推送到 `main`；若 GitHub 分支保护要求 PR，则改用 `codex/v1-<node>` 分支并创建 PR，不绕过保护规则。
9. **标签与回报**：只创建第 3 节预定义标签。完成后向 USER 报告 commit SHA、分支、标签、文件范围、验证结果和未上传材料。

## 6. 公开白名单

经门禁通过后，可以纳入节点提交：

- `project/governance/PROJECT_CHARTER.md`、README、TASKS、CHANGELOG、决策记录；
- 研究规范、Schema、数据字典、审核包、公开验收记录；
- 书目级来源信息、URL、来源题名和机构信息；
- 不含受限长摘录的候选/暂存/正式结构化数据；
- 可公开的 SQLite、CSV/Excel、JSON 导出；
- 项目验证、构建和导出脚本；
- 公开质量报告、覆盖矩阵、版本摘要和已知问题。

## 7. 永久禁止自动上传

- 用户提供的 PDF、EPUB、扫描件、原始书籍和 `inputs/`；
- 整书 OCR、整部诗集/作品全文、论文全文或未授权长摘录；
- `local_only` 文件、私人批注、购买记录和未公开材料；
- Cookie、token、密码、密钥、账号配置、环境文件和凭据；
- 临时目录、缓存、构建中间物、`.DS_Store`；
- 未通过验收的外部 AI 交付及无法确认版权边界的文件。

## 8. 自动流程停止条件

出现以下任一情况时，不提交或不推送，并向 USER 报告：

1. 节点状态、审核 verdict 或用户节点结论不明确；
2. 公开边界无法确定，或发现疑似受版权/隐私限制的文件；
3. 验证失败、版本不一致、数据库与导出不一致；
4. staged diff 出现大量删除、无关文件或未解释的跨模块修改；
5. 远端 `main` 有未知新提交、存在分叉或不能安全快进；
6. GitHub 身份认证、网络、分支保护或 required checks 状态不明确；
7. 操作需要 force push、删除远端对象、历史重写或绕过 hooks；
8. N3/N4 所需的 USER 决定尚未明确作出。

停止只暂停 GitHub 发布，不撤销已经通过的本地项目成果。

## 9. 分支与历史整理建议

- `main` 只保存通过节点的公开里程碑提交；普通任务过程不进入 `main`。
- 当前本地/远端存在的 `publish-sync-project-updates` 分支不在本提案批准时立即删除或改写。到 `GIT-V1-S3` 时先审计其与 `main` 的差异，再用非破坏方式收口。
- 里程碑间的本地工作可以保留在当前工作分支；如果 `main` 受保护，则每个节点使用新的 `codex/v1-s3`、`codex/v1-n3` 等分支和 PR。
- 不为每个外部 AI 任务创建永久远端分支，避免 GitHub 出现大量低价值 WIP 分支。

## 10. 对阶段、任务和数据的影响

- 不改变 V1 目标、作家/作品范围、Schema、证据门槛、用户 N1—N4 审核权或版权边界；
- 不要求重做已完成任务，不迁移或改写现有数据；
- 仅改变通过节点后的 Git/GitHub 触发方式和公开历史组织方式；
- `project/tasks/TASKS.md` 仍是唯一动态状态源；GitHub 只发布已经通过的公开快照；
- 外部 AI 仍不得操作 Git、GitHub、治理文件和正式发布。

## 11. 风险与备选方案

### 推荐方案：节点自动提交和推送

优点：减少 USER 重复指令；GitHub 与项目关键进展同步；提交历史清楚。风险通过白名单、验证和 fail-closed 停止条件控制。

### 备选方案 A：节点只自动提交，不自动推送

更保守，但 GitHub 仍可能落后，需要 USER 继续触发 push。

### 备选方案 B：继续现行逐次用户触发

权限最保守，但沟通成本最高，也最容易形成大量长期未上传变更。
