## 3. 规则表述与实际工程不一致

### 3.1 SQLite 主数据方向

- 文档规则：`project/governance/PROJECT_CHARTER.md:156`、DEC-006 规定 SQLite 是唯一主数据，CSV/Excel/JSON 从 SQLite 生成。
- V1 实际：`scripts/build_v1_candidate.py` 从 PRE/映射/CSV 组装内存表，然后同时写 CSV、JSON、SQLite；Excel从 CSV 生成。
- 判断：V1 的同源构建和一致性验证有效，但“SQLite 唯一写入源”没有落实。
- 当前规则：长期增量必须以 SQLite 为唯一正式写入点；现有脚本只作为 v1.0.0 历史重建器。
- 执行结果：已建立 `data/master/`、迁移脚本、SQLite→导出脚本和动态验证器；在此基线之上，修改 Excel/CSV/JSON 仍不得被称为正式入库。

### 3.2 数据目录

- 规范建议：`data/master/`、`data/exports/`。
- V1 实际：正式发布数据位于 `data/staging/v1_candidate/`。
- 判断：不影响 v1.0.0 历史标签，但不适合继续增量维护。
- 当前规则：历史目录只读；下一次增量先创建正式主库与按版本导出目录，不在 `staging` 原地覆写已发布文件。

### 3.3 验证脚本

- 规则目标：每次增量自动检查不变量和导出一致性。
- V1 实际：`validate_v1_candidate.py` 固定 74/144/76/238、具体 ID 与 N3 决定。
- 判断：它是 v1.0.0 快照测试，不是通用 QA。
- 当前规则：保留该脚本做回归；另建动态验证器，计数从 SQLite 实时读取。

### 3.4 Excel 构建

- 规则目标：全部导出可重复由主库生成。
- V1 实际：Excel 由工作区电子表格运行时从 CSV 生成，仓库没有通用 SQLite→Excel 构建脚本。
- 当前规则：Excel 仍是只读审核层；`scripts/export_from_sqlite.py` 已补齐可重复构建入口，视觉/公式 QA 仍在发布门禁中执行。

### 3.5 URL 核验记录

- 规范要求：网页记录访问日期和访问结果。
- 正式 `sources` 表当前无独立 `verified_at`、`url_status` 字段，访问证据主要散在上游包。
- 当前规则：新增来源任务必须保留核验日期/状态；正式主库应通过兼容迁移补充字段或关联表。

## 4. 流程重复与应淘汰做法

| 建设期做法 | 问题 | 长期替代 |
|---|---|---|
| 每个小任务同步 README、TASKS、决策、CHANGELOG | 重复提交和状态漂移 | TASKS 只记真实任务；治理文件按里程碑/版本同步 |
| 每个任务都使用 FULL 七文件包 | 单条纠错成本过高 | 机械/小增量默认 LITE；高风险才 FULL |
| STATUS、QA、HANDOFF、SUMMARY 各自抄数字 | 多源统计漂移 | 生成一份机器 QA；其他文档链接/引用结果 |
| 为页码完整而逐页补录 | 成本高且非最低门槛 | 来源级定位为最低；页码按任务需要增强 |
| 为数量覆盖所有关系词 | 容易制造弱关系 | 没有证据就留空或 gap |
| 把低置信度当作无来源事实的缓冲 | 置信度不能替代证据 | 无直接来源则删除、candidate、hold 或 gap |
| 单条数据也重跑全 V1 覆盖审计 | 不符合最小增量 | 只跑受影响表及全局不变量；批量/版本节点才跑覆盖审计 |
| 外部 AI 预组装 SQLite 后再由 Codex重建 | 重复且易混淆主权 | Worker 交候选；Integrator 直接用迁移写正式 SQLite |
| 单纯依赖共享机械 pass | 无法识别语义和来源层级 | 机械 QA + 独立语义 Reviewer 双门禁 |
