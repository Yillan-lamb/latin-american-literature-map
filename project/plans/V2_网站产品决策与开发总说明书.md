# 一、V2 产品定位与核心目标

## 1.1 产品定位

拉丁美洲文学地图 V2 定位为：

> **面向中文读者的交互式拉丁美洲文学数字展览，以普通文学读者为主要用户，同时兼顾文学研究者、学生及具有进一步研究需求的用户。**

网站不以建设专业学术数据库或传统文学百科为主要目标，而是利用已有的结构化文学数据，将作家、作品、地点、时代、文学主题、文学运动与历史事件组织为可探索的数字文学空间。

产品整体采取“**普通阅读优先、研究能力下沉**”的双层结构：

- 第一层面向普通文学读者，强调直观、易读、具有探索感；
- 第二层面向具有进一步阅读或研究需求的用户，提供来源、关系依据、研究说明等信息。

## 1.2 核心探索方式

网站以 **地图浏览** 作为最主要的内容入口。

用户首先通过拉丁美洲地图发现不同国家、城市、作家及作品，并沿地点与文学之间的关系继续探索。

在地图之外，网站提供两类辅助探索方式：

- **时间探索**：按照文学时期、作品年代及重要文学节点理解拉丁美洲文学的发展；
- **人物及统一检索**：通过作家、作品、地点、主题、文学运动等快速进入目标页面。

V2 基本产品结构确定为：

> **地图为主入口，时间为纵向线索，搜索为快速入口。**

关系网络本身不作为与地图并列的一级入口，而主要作为作家、作品、地点等内容页面内部的进一步探索机制。

## 1.3 核心产品价值

网站的核心价值包括三个层次。

### 第一，展示拉丁美洲文学的整体特色

通过地图、时间和文学关系，使用户直观感受到不同国家、历史背景、文学传统和地域经验如何共同构成拉丁美洲文学。

### 第二，展示不同作家与作品的独特性

网站不仅回答“有哪些重要作家和作品”，还应帮助用户理解不同作家的创作特征、文学主题、代表作品、重要地点及其所处的文学与历史语境。

### 第三，为阅读和研究提供入口

网站首先承担拉丁美洲文学传播与兴趣引导功能，在此基础上进一步提供：

- 作品阅读路径；
- 相关作家和作品推荐；
- 可追溯的研究来源；
- 初步研究线索。

为文学阅读、课程学习和初步研究提供辅助。

## 1.4 产品设计原则

后续网站设计与开发遵循以下基本原则：

### 易进入

用户无需具备拉丁美洲文学背景知识，也能够理解网站并开始探索。

### 重探索

尽量通过地图、人物、作品和关联内容引导用户不断发现，而不是形成静态百科页面。

### 文学内容优先

数据库结构服务于文学展示，不直接将数据库字段和技术结构暴露给普通用户。

### 研究信息下沉

来源、证据、数据状态等信息应保留，但通过“来源与研究依据”等二级区域展示，不干扰普通阅读。

### 保持可追溯性

网站中的重要文学事实和研究性判断应能够回到项目数据库及其来源依据。

### 传播优先于工具化

V2 首要任务是让更多中文读者理解并产生阅读拉丁美洲文学的兴趣，而不是建设面向专业研究人员的数据分析平台。

# 二、地图结构与空间语义

## 2.1 地图层级

V2 采用“**国家 → 地点**”两级地图结构。

第一层以国家或地区作为主要入口，使普通中文读者能够快速建立拉丁美洲文学的基本地域认知。

用户进入某一国家后，再展开该国家内部的重要：

- 城市；
- 地区；
- 文学地点；
- 相关作家；
- 相关作品。

基本探索路径为：

> **国家 → 地点 → 作家 / 作品 → 进一步文学关联**

例如：

> 墨西哥  
> → 圣加布里埃尔  
> → 胡安·鲁尔福  
> →《佩德罗·巴拉莫》  
> → 科马拉

地图不追求一次性展示全部实体，而应通过逐层展开降低信息密度。

## 2.2 地图空间类型

地图中的地点原则上限定为以下三类。

### A. 作家地理

指与作家文学经历具有较强关联的现实地点，包括：

- 出生地；
- 成长地；
- 长期生活地；
- 重要创作活动地；
- 流亡或迁徙中的重要地点；
- 其他具有明显文学意义的地点。

地点进入地图的判断标准不是“作家曾经去过”，而是该地点对于理解作家的生平、写作或文学身份具有一定意义。

### B. 作品故事空间

指作品故事发生或具有重要叙事功能的现实地理空间。

例如作品明确以某一城市、地区或国家为主要故事背景时，可以建立作品与该地点之间的地图关系。

地图展示重点在于帮助用户理解：

> **“文学故事发生在哪里？”**

### C. 文学虚构空间

指作品内部创造的、具有较高文学识别度和解释价值的虚构地点。

例如：

- 马孔多；
- 科马拉。

虚构地点应与现实地理地点在视觉标识上有所区别，并明确标注“文学虚构空间”，避免用户将其误认为现实城市。

## 2.3 历史事件不设置独立地图空间层

战争、革命、政变等历史事件虽然可以作为数据库实体，并可以与作品建立文学研究关系，但原则上不作为 V2 地图的独立空间类型。

地图的核心任务是展示文学空间，而非完整呈现拉丁美洲历史事件的空间分布。

历史事件与作品之间的关系可以继续保留在：

- 作品内容页；
- 作家内容页；
- 时间线；
- 关系说明；
- 专题策展内容。

但不因历史事件具有具体发生地点，就自动在地图上建立独立历史事件节点。

例如：

> 《世界末日之战》 → 卡努杜斯战争

可以作为作品的历史背景与研究关系继续展示，但无需进一步把“卡努杜斯战争发生地”设置为首页地图的主要文学地点。

## 2.4 地图收录原则

地图遵循：

> **文学意义优先于数据完整性。**

并非数据库中所有 `place` 实体都必须展示在地图中，也并非一个地点只要能够获得经纬度就应进入地图。

地点是否进入地图，应优先判断其对于以下内容是否具有实际展示价值：

- 理解作家的文学经历；
- 理解作品的叙事空间；
- 理解具有代表性的文学虚构世界。

因此，V2 地图是经过策展选择的“文学地图”，而不是数据库全部地理实体的可视化投影。

# 三、作家页面设计

## 3.1 页面定位

V2 作家页面采用“**文学探索式作家页**”，不采用传统百科式资料页。

页面重点不是完整罗列作家的生平资料，而是帮助普通读者快速理解：

- 这位作家为什么重要；
- 其文学创作有什么鲜明特征；
- 应当从哪些作品开始阅读；
- 哪些地点、主题和文学关系有助于理解其创作；
- 如果需要进一步学习或研究，可以从哪些来源继续深入。

作家页面应优先承担：

> **认识作家、产生阅读兴趣、继续探索**

的功能。

## 3.2 作家页面基本结构

### 作家概览

页面首屏展示：

- 中文名；
- 原文名；
- 国家或地区；
- 生卒年份；
- 简洁的文学身份标签；
- 一段面向普通读者的作家导语。

导语不采用百科词条式定义，应尽量回答：

> **“理解这位作家，可以从哪些关键词或文学特征进入？”**

### 从哪里认识他 / 她

展示与作家具有重要文学意义的地理地点。

仅展示符合 V2 地图规则的“作家地理”。

地点应可点击进入对应地点页面或地图状态。

### 读什么

展示作家的核心作品。

原则上不简单罗列全部作品，而应进行策展式排序，例如：

- 推荐入门作品；
- 核心代表作；
- 可继续阅读的其他作品。

如数据允许，可以进一步增加简短阅读提示，例如：

- “适合第一次阅读博尔赫斯”；
- “理解其晚期创作的重要作品”；
- “进入其政治与历史主题的作品”。

此类推荐性文字属于策展内容，不属于研究事实。

### 他 / 她在写什么

通过主题展示作家的主要文学特征。

主题不应仅以标签堆砌，而应优先选择对普通读者具有解释价值的核心主题，并配合简短说明。

### 文学关系

展示与理解该作家真正相关的文学关联，例如：

- 文学运动；
- 相关作家；
- 作品之间的重要联系；
- 重要文学传统。

不要求完整显示数据库中的全部关系，不得将作家页面设计成复杂知识图谱界面。

### 研究与来源

页面底部或折叠区域提供：

- 主要参考来源；
- 相关研究资料；
- 数据来源；
- 必要的关系依据；
- 数据或研究状态说明。

普通用户无需展开该区域即可获得完整的基础阅读体验。

## 3.3 作家页信息优先级

> **文学认识 > 阅读引导 > 地理与主题探索 > 研究证据 > 完整资料**

数据库负责保证内容可靠和关系可追溯，前端页面负责从中选择最具有文学解释价值的内容。

# 四、作品页面设计

## 4.1 页面定位

V2 作品页面采用“**文学导读式作品页**”，不采用传统百科式作品资料页。

页面的核心任务是帮助用户回答：

- 这是一部什么样的作品；
- 它讲了什么；
- 它最值得注意的文学特征是什么；
- 它与哪些地点、主题、作家和文学传统相关；
- 如果对这部作品感兴趣，下一步可以继续读什么。

作品页应承担：

> **激发阅读兴趣、降低阅读门槛、建立文学联系、提供延伸路径**

的功能。

## 4.2 页面基本结构

### 作品概览

首屏展示：

- 中文作品名；
- 原文名；
- 作者；
- 首次出版或发表时间；
- 体裁；
- 国家或地区；
- 一句话作品导语。

### 它讲了什么

提供面向普通读者的简洁作品导读。

原则上以不剧透或轻剧透方式介绍：

- 基本情境；
- 主要人物；
- 叙事起点。

不以完整复述情节为目标。

### 为什么值得读

这是作品页核心模块之一。

重点介绍能够体现作品独特性的内容，例如：

- 叙事结构；
- 语言特点；
- 时间结构；
- 现实与幻想的处理；
- 人物塑造；
- 文学史意义；
- 对拉丁美洲社会、历史或文化经验的独特表达。

每部作品原则上选择最具解释价值的 2—4 个重点。

### 它发生在哪里

展示与作品具有明确文学意义的空间，包括：

- 现实故事空间；
- 重要城市或地区；
- 文学虚构空间。

地点应可以进入地图或对应地点页面。

### 它在讨论什么

展示作品最主要的文学主题。

主题应经过策展筛选，避免把数据库中的全部主题标签直接罗列。

### 文学关联

展示真正有助于理解作品的关联内容，例如：

- 作者；
- 文学运动；
- 重要历史背景；
- 改编作品；
- 相关人物；
- 与其他作品的重要联系。

历史事件可以在作品页中出现，但其功能是解释作品，而不是扩张地图层级。

### 读完之后读什么

V2 设置“**延伸阅读 / 下一本读什么**”策展模块。

推荐关系应尽量给出明确理由，例如：

- 相近主题；
- 相近叙事方式；
- 同一文学传统；
- 同一地域经验；
- 同一作家的进一步阅读；
- 有意识的对照阅读。

推荐关系属于网站策展层，不与数据库中的客观事实关系混为一谈。

### 研究与来源

页面底部或折叠区域展示：

- 书目信息；
- 主要研究来源；
- 数据依据；
- 重要关系的证据说明；
- 必要的数据状态或研究缺口。

## 4.3 作品页信息优先级

> **阅读兴趣 > 文学理解 > 空间与主题探索 > 延伸阅读 > 研究证据 > 完整资料**

作品页不是情节摘要库，也不是文学论文，而是连接普通读者与作品之间的阅读入口。

# 五、地点页面设计

## 5.1 页面定位

V2 地点页面采用“**文学地理页**”设计，不制作普通地理百科。

地点页面的核心任务不是介绍某一国家、城市或地区本身，而是回答：

> **“这个地方与拉丁美洲文学有什么关系？”**

地点页面分为两种基本类型：

- 现实地点；
- 文学虚构空间。

两类页面采用不同的信息结构和视觉标识。

## 5.2 现实地点页面

### 国家页面

国家页面作为地图第一层入口，重点建立用户对该国文学版图的整体认识。

主要展示：

- 一段简短的文学导语；
- 相关核心作家；
- 重要文学城市或地区；
- 与该国关联的重要作品；
- 具有代表性的文学主题或传统；
- 可继续探索的地点和人物。

国家页面不重点展示人口、面积、行政区划等普通地理资料。

### 城市与地区页面

重点回答：

- 哪些作家与这里存在重要文学联系；
- 哪些作品发生在这里；
- 这里为什么对相关作家或作品具有意义；
- 从这里还可以继续进入哪些文学内容。

地点进入完整页面的前提仍然是具有明确文学展示价值。

## 5.3 文学虚构空间页面

文学虚构空间设置独立页面模板，并与现实地点进行明确视觉区分。

页面应明确标识：

> **文学虚构空间**

主要展示：

- 该空间出现在哪部或哪些作品中；
- 由哪位作家创造；
- 其基本文学情境；
- 这个空间承载哪些重要主题；
- 它与现实地点是否存在可解释的文学联系；
- 可以从这里继续探索哪些作品、作家和主题。

虚构空间不以“现实原型考据”作为默认展示重点，除非数据库中已有可靠研究依据且该关系具有较高文学解释价值。

## 5.4 地点页设计原则

> **文学意义 > 地理资料**

> **策展内容 > 数据字段罗列**

> **可继续探索 > 完整百科介绍**

现实地点和虚构地点均应成为连接作家、作品和主题的文学入口，而不是信息终点。

# 六、时间线设计

## 6.1 页面定位

V2 时间线作为地图之外的辅助探索方式，用于帮助用户建立拉丁美洲文学发展的基本时间感。

时间线不承担完整文学史编年功能，也不制作综合性的拉丁美洲历史时间线。

其核心任务是回答：

> **“不同时期，拉丁美洲文学出现了哪些重要作家、作品和文学变化？”**

## 6.2 时间线内容范围

时间线以文学内容为主体，重点展示：

- 核心作家的生卒与重要创作阶段；
- 重要作品的首次发表或出版；
- 重要文学运动、文学思潮及文学阶段；
- 对拉丁美洲文学具有代表意义的文学事件；
- 必要的文学奖项或国际传播节点。

历史事件原则上不作为时间线主体。

只有当某一历史事件对于理解具体作家、作品或文学阶段具有明显解释价值时，才作为背景节点进入时间线。

遵循：

> **文学事件为主，历史事件为辅。**

## 6.3 两级时间结构

时间探索采用：

> **文学时期 → 具体节点**

两级结构。

### 第一层：文学时期

时期划分应服务于普通读者理解，不必机械采用单一文学史分期体系。

例如可包括：

- 现代主义与世纪之交；
- 先锋派与现代文学实验；
- 1940—1950 年代的新小说探索；
- 拉丁美洲文学爆炸；
- 爆炸之后与当代文学。

具体名称和年代边界由后续内容策展根据数据库及研究资料核定。

### 第二层：具体文学节点

进入某一时期后，再展示其中的重要：

- 作家；
- 作品；
- 文学运动；
- 必要历史背景。

每一个节点均应可以继续进入对应的作家页、作品页或相关内容页。

## 6.4 历史事件展示规则

历史事件只有满足以下条件之一时，才建议进入时间线：

- 对某位核心作家的文学经历产生重大影响；
- 直接影响重要作品的创作或文学语境；
- 对某一文学阶段具有明显解释价值。

历史节点在视觉上应弱于文学节点，并明确其背景性质。

## 6.5 时间线原则

> **帮助理解文学发展 > 完整编年**

> **重要节点 > 数量丰富**

> **文学内容 > 历史背景**

> **继续探索 > 静态阅读**

# 七、搜索与内容发现机制

## 7.1 搜索定位

V2 设置统一文学搜索入口。

搜索功能支持项目中的主要文学对象，包括：

- 作家；
- 作品；
- 国家、城市及文学地点；
- 文学虚构空间；
- 文学主题；
- 文学运动。

搜索首先承担：

> **准确找到目标内容**

的功能，同时提供有限的关联发现能力。

## 7.2 搜索结果结构

搜索结果按照内容类型进行区分和展示。

例如搜索“马孔多”，可以显示：

- 文学虚构空间：马孔多；
- 相关作品：《百年孤独》；
- 相关作家：加西亚·马尔克斯。

搜索结果应帮助用户快速判断“这是什么”，避免所有结果以无差别列表形式展示。

## 7.3 搜索优先级

> **准确定位优先，文学发现辅助。**

用户明确搜索某一作家或作品时，应首先返回最直接的对象，不应因为关系数据丰富而把大量关联结果置于目标对象之前。

## 7.4 轻量关联发现

搜索结果可以提供少量“相关探索”内容。

相关探索必须基于：

- 数据库已有关系；
- 经策展确认的推荐。

不得进行不可解释的算法推断。

## 7.5 V2 不建设复杂推荐系统

V2 不开发：

- 用户画像；
- 行为追踪；
- 协同过滤；
- 机器学习个性化推荐。

作品页“读完之后读什么”、搜索页“相关探索”等推荐均采用：

> **数据库关系 + AI/人工策展规则**

实现。

# 八、普通阅读层与研究证据层

## 8.1 双层信息结构

V2 采用：

> **普通阅读层 + 可展开研究层**

的双层信息结构。

普通阅读层负责：

- 文学传播；
- 阅读导引；
- 作家与作品特色展示；
- 地图、时间和文学关系探索。

研究层负责：

- 来源追溯；
- 关系依据；
- 数据审核状态；
- 必要研究说明；
- 研究缺口和不确定性披露。

研究层原则上不干扰普通用户的连续阅读体验，但应保持随时可访问。

## 8.2 基础事实展示

生卒年份、作品首次发表时间、国别、语言、体裁等可靠基础事实，可以直接进入普通页面正文。

此类信息不要求在每一句文字之后显示来源编号。

页面可以在底部“来源与研究依据”区域统一提供主要来源。

## 8.3 文学解释性内容

涉及文学主题、作品意义、叙事特征及实体之间的解释性关系时，应保留研究依据的可追溯能力。

普通页面采用自然语言表达。

如进一步点击“查看研究依据”，可以查看：

- 支持该判断的来源；
- 关系或研究说明；
- 必要的数据状态；
- 相关研究资料。

前端原则上不直接向普通用户展示数据库内部字段名称，例如：

- `EXPLORES_THEME`
- `confidence=medium`
- `accepted_at_n3`

## 8.4 已审核关系

数据库中已经完成审核并进入正式数据层的关系，可以用于：

- 普通页面内容；
- 地图关联；
- 搜索关联；
- 页面推荐；
- 文学关系展示。

如关系具有明显解释性质，应同时保留研究层入口。

## 8.5 Hold 与未确定研究内容

处于 hold、research gap 或其他尚未完成确认状态的内容，原则上：

- 不得直接进入普通正文；
- 不得以普通关系形式展示。

确有策展价值时，可以设置独立区域：

> **研究线索 / 尚待进一步验证**

并明确说明尚未达到项目正式关系的证据标准。

不得因前端展示需要而改变数据库中的审核状态。

## 8.6 展示语言转换原则

数据库负责保存：

- 实体类型；
- 关系类型；
- 来源编号；
- 证据；
- 审核状态；
- 置信信息。

网站负责将其转换为普通读者能够理解的文学语言。

核心原则：

> **研究可靠性存在于后台，文学可读性呈现在前台。**

# 九、视觉系统与首页结构

## 9.1 整体视觉方向

V2 整体采用：

> **当代文学杂志 × 文学档案馆**

的视觉方向。

其中：

- 当代文学杂志感作为主要视觉基调；
- 文学档案馆感作为辅助视觉语言；
- 地图作为网站最重要的视觉与交互元素。

整体应呈现：

> **现代、克制、文学、具有阅读感，同时保留一定研究与档案气质。**

不得将网站设计成传统数据库后台，也不采用过度复古、泛黄纸张式的整体视觉。

## 9.2 当代文学杂志感

主要体现在：

- 大量合理留白；
- 清晰字体层级；
- 具有出版物感的标题排版；
- 适合长时间阅读的正文区域；
- 简洁克制的卡片和导航；
- 少量但明确的强调色；
- 图片、文字与地图之间保持良好版面关系。

## 9.3 文学档案馆感

主要用于：

- 来源与研究依据；
- 书目信息；
- 文献卡片；
- 地图标记；
- 年代信息；
- 研究状态；
- 数据说明。

可以通过编号、细线、书目式排版、文献标签等方式体现。

## 9.4 避免刻板“拉美视觉”

V2 不采用大量：

- 热带植物；
- 艳丽橙红色；
- 旅游海报；
- 殖民建筑；

等元素简单代表“拉丁美洲”。

不得将复杂的拉丁美洲文学压缩为单一的“热情、热带、异域”视觉印象。

## 9.5 动效原则

V2 可以使用适量交互动效，例如：

- 地图区域进入与退出；
- 地图标记展开；
- 页面之间轻量过渡；
- 卡片展开；
- 时间线节点进入；
- 研究依据展开。

遵循：

> **交互反馈 > 装饰动画**

> **稳定阅读 > 视觉炫技**

V2 不以复杂动画、3D 效果或强滚动叙事作为主要产品特色。

---

## 9.6 首页第一视觉中心

首页第一视觉中心确定为：

> **拉丁美洲文学地图**

用户进入网站后，应尽快看到地图，而不是首先阅读大段项目介绍。

首页标题可采用：

> **拉丁美洲文学地图**

并配一条简短项目导语。

具体宣传文案可以在后续内容策展阶段调整，不在开发阶段硬编码为不可修改内容。

## 9.7 首页地图

地图首先展示拉丁美洲国家或地区。

用户点击国家后进入第二级地点与文学内容探索。

地图承担：

- 网站核心识别；
- 国家入口；
- 地点发现；
- 作家发现；
- 作品空间发现。

地图上不得一次性显示数据库全部节点。

## 9.8 精选作家

地图之后设置“精选作家”区域。

第一阶段优先展示 V1 核心作家。

作家卡片应突出：

- 作家姓名；
- 原文名；
- 国家；
- 一句文学特征；
- 进入作家页的明确入口。

不得设计成单纯头像墙。

## 9.9 策展阅读入口

首页设置独立的策展式阅读入口。

其功能是帮助普通读者解决：

> **“我应该从哪里进入拉美文学？”**

例如：

- 第一次读拉美文学；
- 从《百年孤独》开始；
- 从博尔赫斯开始；
- 不止魔幻现实主义；
- 拉美女性作家；
- 城市与乡村；
- 时间、记忆与迷宫。

具体专题由后续内容策展决定。

## 9.10 简版时间线

首页展示简化文学时间线。

仅选择少量具有代表性的作品、作家或文学节点。

其功能是引导用户进入完整时间探索页面。

## 9.11 项目说明

“关于项目”“研究方法”“数据与来源”等内容放置在首页后部或独立页面。

用户无需阅读项目方法即可正常使用网站。

## 9.12 首页信息优先级

> **地图探索  
> → 作家发现  
> → 阅读策展  
> → 时间探索  
> → 项目与研究说明**

首页首先展示文学，最后解释“我们如何研究文学”。

# 十、Web 0.1.0 基线范围与开发边界

## 10.1 首版目标

Web 0.1.0 的首要目标不是建设功能完整的数字人文平台，而是完成一个产品模型成立、可持续扩充的“拉丁美洲文学地图”网站。

首版必须首先验证以下核心体验：

> **发现文学 → 认识作家 → 进入作品 → 沿文学关系继续探索**

只要这一核心闭环成立，即视为 Web 0.1.0 的主要产品目标实现。

## 10.2 Web 0.1.0 必须完成的功能

首版开发范围包括：

- 首页；
- 国家 → 地点两级文学地图；
- 国家页面；
- 现实地点页面；
- 文学虚构空间页面；
- 作家页面；
- 作品页面；
- 统一搜索；
- 文学时间线；
- 首页精选作家；
- 首页策展阅读入口；
- “读完之后读什么”延伸阅读；
- 普通阅读层与可展开研究层；
- 来源与研究依据展示；
- 桌面端与移动端基础响应式适配。

以上功能构成 Web 0.1.0 的核心产品闭环。

## 10.3 Web 0.1.0 暂不开发

以下功能明确不属于 Web 0.1.0 基线开发范围：

- 用户注册与登录；
- 收藏；
- 评论；
- 社交互动；
- 用户画像；
- 个性化推荐算法；
- AI 对话与文学问答；
- 复杂知识图谱可视化；
- 3D 地图；
- 小程序；
- 独立 CMS 管理后台；
- 多语言版本；
- 用户投稿或自行提交数据；
- 高度定制的滚动叙事专题；
- 大规模复杂动画。

如开发过程中发现上述功能具有价值，应登记为后续版本候选，不得因此扩大 Web 0.1.0 范围。

## 10.4 关系网络展示原则

Web 0.1.0 不将复杂知识图谱作为独立核心功能。

数据库中的实体关系主要通过：

- 页面关联内容；
- 推荐卡片；
- 地点跳转；
- 主题跳转；
- 作品延伸阅读；
- 自然语言关系说明；

呈现。

网站首先解决：

> **“用户接下来可以去哪里？”**

而不是首先解决：

> **“如何把数据库中的所有节点和边画出来？”**

## 10.5 首版开发原则

> **先建立完整网站，再增加高级功能。**

> **先保证核心浏览体验，再追求技术复杂度。**

> **先验证内容和交互，再扩大数据和产品范围。**

开发过程中不得因数据库已有某类数据，就默认必须为其设计独立前端功能。

# 十一、V2 数据架构与内容策展层

## 11.1 总体架构

V2 建立：

> **研究数据层 + 策展展示层 + 网站构建层**

三层结构。

基本数据流确定为：

> **研究资料  
> → 研究数据库审核入库  
> → 策展内容补充  
> → 自动生成网站数据  
> → 前端网站展示**

网站不得脱离研究数据库另行维护一套事实数据。

## 11.2 研究数据层 Research Data

研究数据层继续以现有 V1 数据库及其后续版本为事实基础。

主要保存：

- 作家；
- 作品；
- 地点；
- 文学主题；
- 文学运动；
- 历史事件；
- 实体关系；
- 基础事实；
- 来源；
- 证据；
- 审核状态；
- hold；
- research gap。

核心原则：

> **准确、规范、可追溯。**

## 11.3 策展展示层 Curation Data

V2 新增独立策展数据层。

策展数据回答：

> **“现有研究内容应当怎样呈现给普通读者？”**

主要包括：

- 首页精选作家；
- 首页精选作品；
- 首页策展专题；
- 作家页文学导语；
- 作家核心主题排序；
- 作家入门作品推荐；
- 作品阅读导语；
- “为什么值得读”；
- 核心主题排序；
- “读完之后读什么”；
- 推荐理由；
- 地点文学导语；
- 虚构空间说明；
- 时间线节点筛选；
- 页面展示排序；
- 是否进入地图；
- 是否进入首页；
- 展示标签。

## 11.4 研究关系与策展推荐必须区分

研究数据库中的正式关系表达经证据审核的研究判断。

策展层中的推荐表达网站编辑与阅读引导判断。

例如：

> 《百年孤独》 → SET_IN → 马孔多

属于研究数据。

而：

> “喜欢《百年孤独》的时间与乡土书写，可以继续阅读《佩德罗·巴拉莫》。”

属于策展推荐。

不得因为存在策展推荐，就自动生成数据库正式关系。

同样，不得因为数据库存在某一正式关系，就自动认定该关系必须进入首页、阅读推荐或核心内容区域。

## 11.5 网站数据构建层

V2 应由构建脚本从研究数据层和策展数据层生成前端专用网站数据。

建议流程：

> **Research Data + Curation Data  
> → build 脚本  
> → Web JSON  
> → 前端**

Web JSON 应围绕页面需要组织，而不是要求前端直接理解全部研究数据库结构。

## 11.6 单一事实源原则

客观文学事实只允许在研究数据层维护。

前端代码不得硬编码：

- 出版年份；
- 生卒年份；
- 国家；
- 作品作者；
- 作品地点；
- 正式文学关系等事实数据。

发现网站内容错误时，应优先定位：

> **研究数据错误 / 策展数据错误 / 构建逻辑错误**

并在对应层修复。

不得仅修改前端显示内容掩盖上游数据问题。

## 11.7 Web 0.1.0 后端原则

Web 0.1.0 暂不建设传统实时数据库服务和完整 CMS 后台。

第一阶段优先采用：

> **结构化研究数据库 + 策展配置文件 + 构建脚本 + 静态网站数据**

完成正式网站。

## 11.8 核心原则

> **研究层决定“什么可以说”。**

> **策展层决定“重点说什么、怎么说”。**

> **构建层决定“怎样转换成网站可用数据”。**

> **前端决定“用户怎样看到和探索”。**

# 十二、地图数据模型与补充任务

## 12.1 地图数据总体原则

V2 地图不直接等同于研究数据库中的 `place` 实体集合。

研究数据库负责记录文学研究中出现的地点；地图展示层则进一步判断：

- 地点属于什么层级；
- 地点是真实还是虚构；
- 是否具有地图展示价值；
- 应以什么方式出现；
- 与作家或作品之间是什么文学关系。

因此必须坚持：

> **地点存在于数据库 ≠ 地点必须进入地图。**

## 12.2 地点层级字段

V2 为地点补充 `place_kind` 字段。

建议值包括：

- `country`
- `region`
- `city`
- `locality`
- `fictional_place`

例如：

- 墨西哥 → `country`
- 恰帕斯 → `region`
- 利马 → `city`
- 圣加布里埃尔 → `locality`
- 马孔多 → `fictional_place`

具体枚举在开发时可以根据现有地点数据进一步收敛，但不得无限增加细分类。

## 12.3 现实属性字段

V2 增加：

`reality_status`

建议值：

- `real`
- `fictional`

该字段与地点层级分开保存。

## 12.4 地理坐标

现实地点可以增加：

- `latitude`
- `longitude`

坐标主要用于地图定位和交互。

地理坐标属于地图技术辅助数据，不属于文学研究判断。

Codex 可以使用可靠、公开、可追溯的地理数据源进行批量补充，并进行基本机械校验。

坐标来源和更新时间应保留必要记录，避免由 AI 凭记忆生成。

## 12.5 地点所属关系

V2 增加：

`parent_place_id`

用于建立地点层级。

例如：

- 利马 → 秘鲁；
- 恰帕斯 → 墨西哥；
- 圣加布里埃尔 → 墨西哥；
- 阿卡塔卡 → 哥伦比亚。

该关系用于自动实现：

> **国家 → 地点**

两级地图结构。

前端不得通过硬编码方式维护国家与地点之间的归属关系。

## 12.6 地图展示状态

V2 增加：

`map_status`

建议采用三级结构：

- `featured`
- `eligible`
- `hidden`

### featured

具有较强文学意义，适合在主要地图层直接展示。

### eligible

具有文学意义，但不需要在默认地图层突出，可在进入国家、缩放地图或相关内容页面后展示。

### hidden

研究数据库保留，但目前不具有足够地图展示价值，V2 地图不显示。

`map_status` 属于策展展示字段，不属于研究事实。

## 12.7 地图关系语义

地点与作家、作品之间不能只保存“有关联”，还应明确其地图展示意义。

### 作家地理

后台可以根据现有资料进一步区分：

- `birth`
- `childhood`
- `residence`
- `writing`
- `exile`
- `major_literary_association`

第一版普通前端不要求全部细分显示。

### 作品故事空间

建议内部语义：

`story_setting`

### 文学虚构空间

建议内部语义：

`fictional_setting`

## 12.8 虚构空间坐标原则

文学虚构空间原则上不得赋予伪精确现实坐标。

不得因为某个虚构地点具有现实原型研究，就直接将虚构地点坐标设置为某一真实城市或地区的经纬度。

例如不得直接建立：

> **马孔多 = 阿卡塔卡**

虚构空间应采用独立展示机制。

可以包括：

- 在所属国家的文学空间层中展示；
- 使用与现实地点不同的地图标识；
- 在页面中明确标注“文学虚构空间”；
- 如有可靠研究依据，可建立“关联现实地点”关系。

但：

> **关联现实地点 ≠ 两者地理等同。**

## 12.9 现实原型与文学联系

如果研究资料能够可靠支持某一虚构地点与现实地点之间存在文学联系，可以在研究数据库中保存相关研究关系或说明。

该关系属于文学研究内容，需要满足项目既有来源和审核标准。

不得为了地图展示需要自行推定现实原型。

## 12.10 V2 地理数据补充任务分类

### A. 可自动补充的技术数据

原则上由 Codex 或脚本完成：

- 现实地点经纬度；
- 基础地理层级；
- 国家代码；
- 坐标格式；
- 地理数据一致性校验。

必须使用可靠公开来源，不允许 AI 凭记忆生成。

### B. 需要研究判断的数据

需要按照现有研究与证据标准审核：

- 某地点是否对作家具有重要文学意义；
- 某作品是否确实以某地点为主要故事空间；
- 虚构地点与现实地点是否存在可支持的文学关联；
- 地点关系具体属于何种文学语义。

### C. 策展决定

属于 V2 策展层：

- 是否进入地图；
- `featured / eligible / hidden`；
- 默认地图显示顺序；
- 哪些地点作为国家页面核心文学地点；
- 哪些地点值得设置完整地点页面。

## 12.11 Codex 地图开发前置要求

Codex 在地图开发前应首先完成：

1. 盘点现有全部 `place` 实体；
2. 建立 V2 地理补充表或对应结构；
3. 区分现实地点与虚构地点；
4. 为现实地点补充可靠坐标；
5. 建立国家与子地点层级；
6. 标识当前缺失的文学地点关系；
7. 生成地图数据 QA 报告；
8. 完成后再进入正式地图组件开发。

不得先在前端手工填写地点坐标，再回头补数据库。

## 12.12 核心原则

> **现实地点用真实地理数据定位。**

> **虚构空间保留文学虚构属性。**

> **文学关联需要研究依据。**

> **地图是否展示属于策展决定。**

> **前端不得通过伪造坐标或硬编码关系解决上游数据缺口。**

# 十三、技术架构与部署原则

## 13.1 技术选型原则

Web 0.1.0 不在产品决策阶段预先锁定 Next.js、Astro、Vue 等具体前端框架。

Codex 有权根据：

- 项目现状；
- 地图组件需求；
- 静态生成能力；
- 维护成本；
- 后续扩展需求；

自主选择成熟、稳定的技术方案。

但最终方案必须满足本章确定的技术目标和产品边界。

## 13.2 静态优先

Web 0.1.0 采用：

> **静态优先**

的技术策略。

由于首版不包含：

- 用户账户；
- 评论；
- 收藏；
- 用户投稿；
- 在线编辑；
- 个性化推荐；
- 实时业务数据；

原则上不应为了技术完整性额外建设复杂后端服务。

优先考虑：

> **研究数据库 + 策展数据  
> → 构建脚本  
> → Web JSON / 静态页面数据  
> → 网站构建  
> → 静态部署**

## 13.3 数据读取原则

前端原则上读取构建后的 Web 数据，不直接承担研究数据库的数据清洗和业务判断。

前端不得自行：

- 纠正研究数据；
- 推断实体关系；
- 生成文学事实；
- 补充缺失坐标；
- 修改审核状态。

## 13.4 地图技术要求

地图技术方案由 Codex 自行评估，但应满足：

- 支持拉丁美洲国家级地图展示；
- 支持国家 → 地点两级探索；
- 支持现实地点点位；
- 支持文学虚构空间的差异化展示；
- 支持移动端；
- 支持基本地图交互；
- 可根据数据自动生成节点；
- 不依赖大量前端硬编码；
- 具备长期维护能力。

地图视觉应服务于文学内容，不追求 GIS 专业系统级功能。

## 13.5 性能原则

Web 0.1.0 应优先保证：

- 首页快速加载；
- 地图交互流畅；
- 页面跳转自然；
- 搜索响应及时；
- 手机端可正常浏览。

不得因为一次性加载全部实体、全部关系和全部研究证据而显著降低首页性能。

## 13.6 响应式要求

Web 0.1.0 必须同时支持：

- 桌面浏览器；
- 平板设备；
- 主流手机浏览器。

移动端不得仅视为桌面页面的缩小版。

尤其需要针对以下内容独立适配：

- 地图操作；
- 作家和作品卡片；
- 搜索；
- 时间线；
- 来源展开；
- 导航。

## 13.7 部署原则

网站应部署至满足以下条件的平台：

- 可公开访问；
- 支持 HTTPS；
- 支持自动化构建；
- 与 GitHub 工作流兼容；
- 更新成本较低；
- 适合静态网站长期运行。

具体部署厂商由 Codex 根据最终技术栈决定。

## 13.8 GitHub 权威来源

现有 GitHub 仓库继续作为项目公开版本历史的重要权威来源。

网站开发应延续现有版本管理纪律。

原则上应做到：

> **数据变化可追溯  
> → 策展变化可追溯  
> → 代码变化可追溯  
> → 网站版本可追溯**

不得将重要生产版本仅保存在个人本地环境。

## 13.9 自动构建

Codex 应尽量建立自动化构建流程。

理想流程为：

> **Research Data 更新  
> → 数据审核  
> → Curation Data 更新  
> → Web 数据构建与校验  
> → 网站构建  
> → 自动化测试  
> → 部署**

## 13.10 技术选型权限

Codex 可以自行决定：

- 前端框架；
- CSS 方案；
- 地图库；
- 搜索实现方式；
- 静态生成方式；
- 项目目录结构；
- 构建工具；
- 部署平台。

但不得自行改变已经确定的：

- 产品定位；
- 页面结构；
- 地图语义；
- 数据分层；
- 研究证据规则；
- Web 0.1.0 功能边界。

如技术限制导致必须修改上述产品决策，应形成明确说明并提交新的用户决策，不得在开发中静默改变。

# 十四、图片与视觉素材政策

## 14.1 作家照片

Web 0.1.0 可以使用作家照片，但原则上仅使用：

- 已进入公有领域的照片；
- 具有明确开放许可的照片；
- 其他能够确认具有合法公开展示授权的素材。

不得仅因图片能够在搜索引擎或普通网站中公开访问，就默认可以直接用于本项目。

Codex 在引入作家照片时，应尽量保留：

- 图片来源；
- 作者或摄影者；
- 授权或版权状态；
- 原始页面链接；
- 必要署名要求。

无法确认使用条件的图片，不进入正式网站。

## 14.2 作品封面

Web 0.1.0 原则上不使用商业出版版本的作品封面作为主要视觉素材。

作品页面优先通过：

- 中文书名；
- 原文书名；
- 作者；
- 年份；
- 体裁；
- 排版；
- 地图与文学信息；

建立文学出版物式视觉。

作品页面不得因为缺少封面图片而阻断开发。

## 14.3 无图片情况下的设计原则

如果某位作家没有适合公开使用的照片，网站不得为了视觉完整性使用来源不明图片。

可以改用：

- 姓名排版；
- 原文名；
- 年代；
- 国家；
- 文学关键词；
- 地图元素；
- 文字与版式设计；

完成页面视觉。

## 14.4 素材优先级

> **版权状态明确  
> > 来源可靠  
> > 与文学内容相关  
> > 视觉质量  
> > 是否有图片**

版权和来源要求优先于视觉丰富度。

# 十五、AI 策展内容生成与审核机制

## 15.1 AI 策展角色

V2 的策展内容原则上允许由 AI 根据现有研究数据库和正式来源生成初稿。

包括：

- 作家文学导语；
- 作品阅读导语；
- “为什么值得读”；
- 核心主题说明；
- 国家与地点文学导语；
- 入门作品推荐；
- “读完之后读什么”；
- 推荐理由；
- 首页专题；
- 时间线节点说明。

通过 AI 生成策展草稿，可以降低逐页人工写作成本，提高网站建设效率。

## 15.2 有明确依据的策展内容

当策展内容能够直接由以下材料支持时：

- 已审核研究事实；
- 已审核实体关系；
- 正式来源；
- 已通过的内容卡；
- 明确书目信息；
- 已有文学研究结论；

Codex 可以自行完成：

> **生成 → 来源核验 → 内容审核 → 准入策展层**

无需每条提交 USER 逐项审批。

但 Codex 必须确保：

- 不改变原有研究结论；
- 不把推测写成事实；
- 不超出来源能够支持的范围；
- 不因宣传效果夸大文学评价。

## 15.3 缺乏明确依据的策展判断

以下内容如缺乏现有明确依据，应进入 USER 审核：

- 较强价值判断；
- 对作家文学地位的新概括；
- 对作品特色的原创性解释；
- 跨作品比较；
- 推荐阅读路径；
- “如果喜欢 A，可以读 B”等策展推荐；
- 新的主题归纳；
- 数据库尚不存在依据的文学关系。

AI 可以生成候选草稿和推荐理由，但不得自行作为正式网站内容发布。

## 15.4 审核分层

策展内容采用三类状态：

### `auto_approved`

具有明确研究依据，Codex 已完成来源核验，可以自动准入。

### `user_review`

存在明显策展判断、价值判断或跨内容推荐，需要 USER 审核。

### `hold`

依据不足、表达存在争议或当前不适合正式展示。

## 15.5 AI 不得修改研究事实

AI 在策展过程中如果发现现有研究数据不足，不得为了完成页面直接创造事实或正式关系。

应将问题路由至：

- 研究补证；
- 数据修正；
- research gap；
- USER 策展审核。

策展任务不能绕过研究数据库的证据标准。

## 15.6 核心原则

> **有依据的内容，提高自动化。**

> **无明确依据的判断，保留用户决策。**

> **AI 可以写草稿，但不能用写作替代研究。**

> **策展效率不得牺牲研究可靠性。**

# 十七、Codex 开发启动要求

## 17.1 开发启动总原则

V2-N1 通过后，Codex 不应立即无边界开发完整网站。

开发顺序必须遵循：

> **数据审计 → V2 数据补充 → 策展层最小建立 → Web 数据构建 → N2 核心原型 → USER 审核 → 完整开发**

不得跳过数据与产品验证直接进入大规模页面开发。

## 17.2 第一阶段：V2 数据审计

Codex 首先对 V1.0.0 正式数据进行网站适配审计。

至少检查：

- 当前作家实体；
- 当前作品实体；
- 当前地点实体；
- 当前主题；
- 当前文学运动；
- 当前关系；
- 当前内容卡；
- 当前来源；
- 当前 hold / gap；
- 哪些数据可直接支持 V2 页面；
- 哪些页面内容目前缺失。

形成：

`V2_DATA_READINESS_AUDIT.md`

至少回答：

1. 当前数据可以直接生成哪些页面；
2. 哪些页面缺少关键事实；
3. 哪些地图字段需要补充；
4. 哪些策展字段需要新增；
5. 哪些内容可以自动生成；
6. 哪些事项需要 USER 后续审核。

## 17.3 第二阶段：地图数据准备

按照第十二章完成：

- place 盘点；
- 现实/虚构分类；
- 地点层级；
- 坐标补充；
- parent place；
- map status 候选；
- 地图关系语义；
- 地图 QA。

没有可靠坐标的现实地点不得由 AI 猜测。

虚构空间不得伪造现实坐标。

## 17.4 第三阶段：建立最小策展层

在 N2 原型前，不要求一次性完成全部 40 张内容卡的完整策展。

只需先为 N2 原型选取代表性内容完成最小策展数据。

建议至少覆盖：

- 2—3 个国家；
- 3—4 位作家；
- 4—6 部作品；
- 2 个现实地点；
- 1—2 个文学虚构空间；
- 少量时间线节点；
- 少量阅读推荐。

优先选择现有数据最完整、文学特征最鲜明的对象。

可优先考虑：

- 豪尔赫·路易斯·博尔赫斯；
- 加西亚·马尔克斯；
- 胡安·鲁尔福；

- 《佩德罗·巴拉莫》；
- 《阿莱夫》；

- 马孔多；
- 科马拉。

具体样本由 Codex 根据数据完整性确定。

## 17.5 第四阶段：Web 数据构建

建立 Research Data + Curation Data → Web JSON 的可重复构建流程。

至少满足：

- 页面数据可自动生成；
- 前端不硬编码研究事实；
- 数据结构有明确 Schema；
- 构建过程有 QA；
- 研究数据更新后可重复构建；
- 策展数据与研究数据来源可区分。

## 17.6 第五阶段：V2-N2 核心原型

N2 原型必须使用真实数据，不得仅使用 Lorem Ipsum 或虚构示例。

原型重点验证：

- 首页第一屏；
- 地图视觉；
- 国家 → 地点交互；
- 作家页阅读体验；
- 作品页导读体验；
- 地点页文学空间体验；
- 普通阅读层 / 研究层切换；
- 移动端基本表现。

N2 的目标是：

> **尽早验证“产品是不是我们想要的样子”，而不是尽早把全部功能写完。**

## 17.7 N2 通过前的限制

在 USER 通过 V2-N2 前，Codex 原则上不得：

- 大规模生成全部策展文案；
- 为全部实体开发复杂页面；

- 建复杂关系图；
- 做 3D 地图；
- 搭 CMS；
- 搭用户系统；
- 大规模优化非核心动画。

如某项技术基础工作必须提前完成，可执行，但不得因此扩大产品范围。

# 十八、Web 0.1.0 验收总标准

Web 0.1.0 是否成功，不以代码量、页面数量或功能数量判断。

最终至少满足以下标准：

## 18.1 产品标准

普通中文读者进入网站后能够：

1. 理解这是一个拉丁美洲文学网站；
2. 从地图开始探索；
3. 进入国家或文学地点；
4. 认识核心作家；
5. 进入代表作品；
6. 理解作品的基本文学特色；
7. 找到下一步阅读或探索方向；
8. 在需要时查看来源与研究依据。

## 18.2 文学标准

网站应突出：

- 拉丁美洲文学的多样性；
- 作家个体特征；
- 作品独特性；
- 文学空间；
- 文学主题；
- 阅读路径。

不得将拉丁美洲文学简单归结为“魔幻现实主义”。

## 18.3 数据标准

- 正式展示事实可回溯；
- 已审核关系与 hold 明确区分；
- 前端不单独维护事实；
- 虚构空间不伪装成现实地理；
- 来源与策展层边界明确。

## 18.4 技术标准

- 桌面端正常；
- 移动端正常；
- 地图交互流畅；
- 搜索可用；
- 页面加载合理；
- 构建可重复；
- 部署可维护；
- GitHub 版本可追溯。

## 18.5 内容标准

普通页面首先具有文学可读性。

研究信息保持可追溯但不过度打扰。

AI 生成的策展文字必须经过本文件规定的审核机制。

## 18.6 版权标准

- 作家图片版权状态明确；
- 作品封面不作为 Web 0.1.0 默认素材；
- 不公开原书、整书 OCR、论文全文或其他受限内容；
- 公开引用与短摘录继续遵守项目既有版权规则。
